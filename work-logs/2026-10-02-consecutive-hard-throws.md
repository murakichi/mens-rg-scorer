# 作業ログ 2026-10-02: 生成：高難度の投げを2本続けない（連続投げの安いほうを元に戻す）

- 日付: 2026-10-02
- 実施者: 手動（オーナー依頼）
- 対象issue: なし（依頼「高難度の投げの後に連続して高難度の投げを実施している例が見受けられます。不要です」）

## 調べたこと

- 連続する投げの徒手ユニットが**両方D難度以上**になっている組を数えた
  （`analyzeSeries(ser).units` の `type === "throw" && !isThrowTumbling` を順に見る。
  難度のフィールドは `difficulty` ではなく **`finalDiff`** — 最初に間違えて全部0が出た）
- 出るのは**上限3.5 と 3.5〜4.0 だけ**で、形は文字どおり
  「投げ→シェネ×3→キャッチ→投げ→シェネ×3→キャッチ」:

  | 上限 | 連続投げ | 両方D以上 |
  | --- | --- | --- |
  | 2.5 / 3.0 | 10〜21組 | 0 |
  | 3.5 | 11〜22組 | **5〜18** |
  | 3.5〜4.0 | 21〜32組 | **16〜22** |
  | 4.2以上 / 上限なし | 23〜32組 | 0 |

- 原因は前日（PR #127）に入れた `leadThrowCheneCount`。連続投げの安いほうを
  「水準の1段下」に合わせるもので、天井がEになる 3.5 以上で初めて回数が3に上がる。
  1本目のほうが難度が高い割合も上限3.5で 3/22 まで落ちていた（本来 83%）
- 判断：この形は**操作をほとんど足さずに投げ方を1種類稼ぐ**ために実施するもの
  （`trailPair` は「徒手は1本目、2本目は徒手なしの投げ→キャッチ」）。水準に合わせて厚くするのは
  形の目的と矛盾する。オーナーの優先度も明確（連続高難度＝「不要」、難度を揃える＝「可能な限り」）
  なので、**揃えるほうを譲る**

## やったこと

  `leadPair` の1本目を `LEAD_THROW_CHENE_COUNT`（1回）に、`trailPair` の2本目を徒手なしに戻した
- `src/scoring/generateWeights.ts`: `leadThrowCheneCount` を削除
- `src/scoring/generateSearch.ts`: `autoPool` が渡していた `leadCheneCount` を削除

  - 「生成した構成に『高難度の投げ→高難度の投げ』が出ない」を追加
  - 幅のテストは**前提が変わった**ので実測値に書き換え（5〜14/25 → 15〜22/25、しきい値 0.5 → 0.8）

  実測の表つきで残した（同じ罠を踏み直さないため）

## 気づき・申し送り

- 残りの低いユニットは**単独の最小形の投げ**（投げ→キャッチ ＝ A、投げ→1シェネ→キャッチ ＝ B）。
  連続投げではないので厚くしても今回の規則には触れないが、これは 必須投げ をいちばん安く
  満たす形＝加点のための投げと同じ形なので、潰すとオーナーの別の要望に反する。
  本筋は「安い投げを上位3つに入れない（徒手ユニットを4つにする）」ほうで、
  上限いっぱいだとDスコアが足りない。起票した: #129
- 教訓：**昨日の指標を上げるために入れた変更が、既に文書化されていた別のドメイン規則
  （「連続投げは1回目で難度を採る」）を壊していた。** 指標を動かす変更を入れるときは、
  その形が何のために存在するかを `CLAUDE.md` で読み直すこと
