# 作業ログ 2026-09-30: Dスコア4.2以上は「6ユニット全部E」を加点より先にした

- 日付: 2026-09-30
- 実施者: 手動（オーナーの指示「4.2以上を狙うときは上位6シリーズを全てEにしてから加点を狙う」）
- 対象issue: なし（作業中に #122 を起票）

## 調べたこと

**4.2 は E難度 0.7 × 6ユニット（上位3タンブリング＋上位3徒手）ちょうど**。
`DIFF_SCORE.E` = 0.7、`ADOPT_COUNT` = 3 なので 0.7 × 3 × 2 = 4.2。
つまり 4.2 以上は「6つ全部E」が必要条件で、それを超えるぶんが加点。指示はこの構造そのもの。

実測（手具ごと25構成・下限4.2）：6つ全部Eになったのは **9〜14/25** しかなかった。
内訳を見ると**タンブリングはほぼE**（69〜74/75）で、**徒手側が届いていない**（60〜67/75）。

原因はタンブリングのときと同じ2つ：

- 貪欲法は投げの枠が埋まったあとに出てきた候補を見られない
- `tuneAutoThrows` は選ばれた形のシェネ回数しか動かせず、**最小形の投げ（1シェネ）は伸ばせない**

徒手ユニットがEになるのは `calcHandDifficulty`（A難度 ＋ 動作数）より **4動作**または縦3動作。

## やったこと

- `generateWeights.ts`
  - `topDifficulty(future)` / `allEScore(future)` — 4.2 を定数から導く（直書きしない）。
    十年後モードでは「その時代の最高難度 × 6」に自動で上がる
  - `aimsAllE(opts)` — 要求した**下限**が `allEScore` 以上か（上限だけの指定では狙わない）
  - `ALL_E_SHORTFALL_WEIGHT`（0.5）/ `HAND_UPGRADE_ROUNDS`
- `generateEvaluate.ts`: `allEShortfall(r)`（6 − 採用かつ上位3のE難度ユニット数）を
  `ALL_E_SHORTFALL_WEIGHT` で引く。加点1つ（0.1）より重く、投げ本数の重み（0.2〜0.3）も上回る
- `generateSearch.ts`: `isHandThrowSeries` / `upgradeHandUnits`（`upgradeTumblings` の徒手版）
- `generate.ts`: ⑦ のタンブリング入れ替えの直後に ⑦' として実行

## 確認

実測（同条件・下限4.2）：

| 手具 | 6つ全部E 前→後 | D平均 前→後 | 採用徒手ユニットのE 前→後 |
| --- | --- | --- | --- |
| スティック | 14/25 → **20/25** | 4.73 → 4.92 | 67/75 → 74/75 |
| クラブ | 12/25 → **24/25** | 4.89 → 5.22 | 63/75 → 75/75 |
| リング | 10/25 → **18/25** | 4.77 → 5.08 | 60/75 → 72/75 |
| ロープ | 9/25 → **22/25** | 4.77 → 5.07 | 60/75 → 74/75 |

伸びはすべて徒手側（タンブリングは前後とも 69〜74/75）。
残るE未満は 75本中 1〜4本、すべて**D難度＝あと1段**（ほぼ通常タンブリング、投げタンは1本）。
下限を指定しない構成は一切変わらない（パスも評価の項も `aimsAllE` で閉じている）。

- `npm test`: 730 tests（`sideThrow.test.ts` の1件が不安定。下記）
- `npm run build`: 成功

### 試して駄目だったこと

`autoThrowSpecs` をシードなしで呼んでいて、閾値 0.75 が標本のばらつきの境目にある
（落ちたときの値 0.7493917274939172）。範囲外なので直さず **issue #122** を起票した。
