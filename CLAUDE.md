# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Vite + React + TypeScript single-page app that calculates competition scores for Japanese **men's rhythmic gymnastics** (男子新体操) — 個人 (individual) and 団体 (team, 5-person) modes. The UI language is Japanese; domain terms below keep the Japanese names since they appear throughout the code.

Two rule documents live at the repo root — keep both and `src/scoring/constants.ts` in sync:
- **`mens-rg-rules.md`** — official scoring rules (2025 edition) translated from the PDF. Pure rules, no code references.
- **`app-scoring-spec.md`** — maps rules to app code: constant names, pipeline description, implementation status, TODOs.

## Commands

- `npm run dev` — Vite dev server (hot reload).
- `npm run build` — `tsc -b` typecheck (strict) then `vite build` to `dist/`.
- `npm run typecheck` — types only, no emit.
- `npm run preview` — serve the production build locally.
- `npm test` — vitest (single run); `npm run test:watch` to keep it running.

The scoring logic is covered by vitest suites in `src/scoring/__tests__/` (analysis / score / team / junior / templates / generate / tags / options / twist). **After changing scoring logic, add or update a test there and run `npm test` plus `npm run build`.** `test-reports/` holds the reports written by the `scoring-test` skill (`.claude/skills/scoring-test`), which walks one rule-compliance pass: compare `mens-rg-rules.md` against `src/scoring/`, add tests for an angle no past report covered, and file an issue for anything wrong.

## Deployment

GitHub Pages via `.github/workflows/deploy.yml` (builds on push to `main`, uploads `dist/`). The Pages source must be set to **GitHub Actions**. `vite.config.ts` sets `base: "/mens-rg-scorer/"` — this must match the repo name or assets 404 on Pages.

## Architecture

The codebase splits cleanly into **pure scoring logic** (`src/scoring/`) and **UI** (`src/App.tsx` + `src/components/`). The UI holds state and renders; it contains no scoring math.

`App.tsx` is a thin shell holding a `mode` toggle and rendering either `IndividualScorer` (個人) or `TeamScorer` (団体, 5-person). Each scorer owns its own state. Styling is a **glassmorphism design system in `src/index.css`** (CSS custom properties + class names + hover/transition states) — components use `className`, not inline styles. Change visual tokens in the `:root` block. Series input (`.skill-row`/`.skill-block`) is a horizontal flow on wide screens and **stacks vertically at ≤720px** (the `.arrow` connector rotates to point down), so phones never scroll sideways. Each item block ends with an `.item-actions` row — `.move-btn` arrows at both ends swap the item with its neighbour (`SeriesListEditor`'s `moveItem`, disabled at the ends; the arrows rotate to ↑↓ in the stacked layout) and the ✕ in the middle removes it.

The data model is a flat **list of `Series`**, each an ordered list of `items` (`src/scoring/types.ts`). Everything else is derived. Five item `kind`s (a discriminated union on `kind`):

- `throw` (投げ) / `catch` (キャッチ) — bracket an apparatus throw; `reqTypes` holds required throws (e.g. `twothrow`, `lefthand`), `throwTypes`/`catchTypes` hold optional technique tags.
- `skill` (タンブリング技) — a tumbling element referencing `SKILL_LIST` by `skillId`, with `hasApparatus` and `isThrow` (throw executed mid-skill) flags. Saltos can also be entered **parametrically** — base (後方宙返り/前宙) × ひねり回数 × 姿勢 (抱え込み/屈伸/伸身) — and the picker switches between the flat list and that builder (a 手動入力／一覧入力 button per block). `buildTwistSkillId` returns the existing `SKILL_LIST` id whenever the combination has one, so dedup signatures never split; only combinations missing from the list become a synthesized `tw:<base>:<twist>:<posture>` id, which `skillDef()` resolves into a full `Skill` via `twistName`/`twistDifficulty`. Difficulty follows §3.6.2: backward depends on twists alone, forward is one step higher for 伸身 (`twistDifficulty`). The list/builder choice is **per skill block** and defaults to the list (switching one leaves the other blocks alone, and nothing is remembered across blocks or reloads); only a synthesized `tw:` id opens in the builder, since the list can't edit it.
- `ropeJump` (ロープ跳び, rope only) — a jump from `ROPE_JUMPS` (`jumpId`) with an `isMoving6m` flag. The series' highest-difficulty jump becomes its own 徒手系 unit (`Unit.fromRopeJump`), and the jumps drive rope's four auto-judged §3.2 elements plus the 様々な跳び加点.
- `motion` (徒手動作) — empty-hand body motions referencing `MOTION_OPTIONS` (`HAND_MOTIONS` plus the 転回技 that can count as 徒手 — 側転/バク転/きりもみ etc.; `motionDef()` resolves either). Each carries a repeat `count` (blank in the UI = 0, and a 0-count motion is counted nowhere — see `motionTimes`) and, for シェネ, a `hands` flag plus a `handsType` (片手上げ/両手上げ/回旋/その他) — hands/no-hands and each hands type are different techniques (Q&A Q28), a unit mixing them gets one signature per variant so it collides with any of them (Q&A Q21), and その他 sets `Unit.neverDuplicate` so it never counts as a duplicate.

### The scoring pipeline (`src/scoring/`)

- **`constants.ts`** — all definition tables and tunable rule values (`SKILL_LIST`, `HAND_MOTIONS`, `DIFF_SCORE`, `*_BONUS`, `*_DEDUCTION`, `*_CAP`, `ADOPT_COUNT`, …). Change scoring values **here only**. Dropdown grouping lives here too: `skillOptionGroups(junior, flow)` splits tumbling skills into 前方系/側方系/後方系 (`SKILL_CATEGORY_ORDER`) and `motionOptionGroupsFor(prevMotionId)` splits 徒手動作 into 縦回転/横回転 (`MOTION_AXIS_GROUPS`; every 転回技 used as 徒手 is vertical) — both keep the existing within-group ordering, and the pickers render them as `optgroup`s.
- **Which 系統 can follow which (input aid, no score effect)** — `leadsBackward(prevSkillId)` (`constants.ts`) answers "does this skill finish facing backward": true for `BACKWARD_ENTRY_SKILLS` (ロンダート/バク転), for backward saltos with whole-number twists, and for **forward saltos with a half twist** (前宙半ひねり — you land facing back, so 後方系 can follow directly); false for backward half-twists (`twist % 1 !== 0`) and `FORWARD_LANDING_BACK_SALTOS` (ダイビング前宙). It only decides whether a ロンダート is needed, not what is offered: the **only** place the picker narrows is right after a ロンダート/バク転, where 後方系 is the sole group (`skillFlowAfter(prevSkillId)` returns the `SkillFlow` — `backward`/`forward`/`side` — that `skillOptions`/`skillOptionGroups` filter by, and a skill that's already selected stays in the dropdown as its own option). Everywhere else all three groups stay selectable — going back to 前方系 after a salto is impractical but possible — and when 後方系 is picked where `leadsBackward` is false the editor **inserts a ロンダート**: `needsRoundoffBefore(items, iIdx)` (`analysis.ts`) tells `SeriesListEditor.updateItem` to splice a `roundoffItem()` in front (a standing バク転 with nothing before it is left alone). Team mode reuses `skillFlowAfter` for the same filter but does not auto-insert (the lane is a fixed grid of slots).
- **`analysis.ts`** — per-series functions. `analyzeSeries(series)` is the heart: it walks `items` left-to-right and flushes a buffer into **units** whenever a `catch` is seen, and also at a 徒手 element that sits *between* tumbling skills (`unitSplitFlags`) — 前宙→前転→前宙 is three units (tumbling / hand / tumbling), each judged on its own, and the salto chain breaks there too. A 徒手 with no 転回技 on one side (the 前転 you land a 投げタン with) does not split, and **nothing splits while a throw is in the air**: between 投げ and キャッチ a mix of 徒手 and タンブリング keeps its existing judging as one chunk.
  - A run with **no throw** → a `tumbling` unit; `calcTumblingDifficulty` = first skill's value, +1 per additional non-A skill, +1 if any throw, capped at E.
  - A run **containing a throw** → a `throw` unit; difficulty is `max(handDiff, tumblingDiff)`. `calcHandDifficulty` derives hand difficulty from accumulated motion count (縦3動作 → forced E). A throw unit that also contains a skill is a **投げタン** (`isThrowTumbling`) and counts toward tumbling, not hand.
  - Also: `saltoFlags` (きりもみ/きりもみ転回 count as saltos only inside a salto chain — Q&A Q7 — and every salto test goes through it), `tumblingFlags`/`handMotionsOfSkill` (a skill that isn't 転回系 — an A skill outside a つなぎ, a standalone きりもみ — counts as 徒手 motions instead: A/きりもみ = 1, きりもみ転回 = 2, summed with the `motion` items; a unit with no 転回系 skill becomes a hand unit even without a throw), `maxSaltoChain`, `hasConnect`/`hasConnectWithoutApparatus` (つなぎ技 detection), `checkApparatusFlow` (in-hand/in-air validator, warnings only — no score effect), `seriesSignature` (dup detection).
- **`score.ts`** — `computeScore(series, apparatus, opts): ScoreResult` is the single source of truth for the whole-routine **individual** score. `opts.junior` switches to the ジュニア適用規則 (§10 変更規則1): ダイビング前宙/後方宙返り半ひねり/後方伸身宙返り半ひねり are C instead of B (`JUNIOR_SKILL_DIFFICULTY`, read via `skillDifficulty(id, junior)`), the minimum throw count drops from 3 to 2 (`throwCountRequired(junior)`), 2回宙返り系 are hidden from the skill picker (`Skill.isDoubleSalto` / `skillOptions(junior)`), and throws are capped at 5 (`throwCountMax(junior)`) — the 6th onward count for nothing (difficulty, throw count, variety, required throws, technique bonus) and cost −0.3 each. The flag is threaded down to `analyzeSeries` / `calcTumblingDifficulty` and defaults to `false`. **Team mode has junior too**: the flag lives in `TeamState.junior` (round-trips through `normalizeTeamState`) and `computeTeamScore` passes it to `analyzeTeamSeries` / `calcChunkDifficulty` / the bonuses — same per-skill difficulties and double-salto ban, plus `JUNIOR_SKILL_COMBOS` (`juniorComboAt`), which judges バク転→後方伸身宙返り as a single C and takes the max against the plain chain and the 5-person bump. Junior also caps each series' execution deduction at 1.0 (`JUNIOR_SERIES_EXECUTION_MAX` via `clampSeriesExecution`) — **team only**; individual series and both modes' whole-routine deductions are uncapped. The UI calls it once (memoized) and renders the returned object. Final score = **D (難度, additive) + A (10 − deductions) + E (10 − manual execution deductions)**, both A and E floored at 0.
- **`team.ts`** — the 団体 (5-person) model and `computeTeamScore(team): TeamScoreResult`. Different data shape: a grid of `Series` × player `lanes` × `slots` of `Cell`s; horizontally-adjacent non-empty cells form a **chunk** whose difficulty reuses `SKILL_LIST`/`DIFF_*` (no throw +1, unlike individual). Team 徒手 is a different thing from individual 徒手: there is no apparatus, so the motion-count options are gone — a `motion` cell picks from the §3.6.1 table (`HAND_ELEMENTS`, 跳躍/バランス/倒立/柔軟) and scores its **団体 (5名実施)** value (`teamHandDifficulty`), never chains with neighbouring cells, and is not bumped by the 5-person rule. 徒手 also presumes all five members perform it, so it is a property of the series, not of a cell: `TeamSeries.content` is `"skill"` (転回 grid) or `"motion"`, toggled next to the 同時実施シリーズ button, and a 徒手 series is `mode: "allTogether"` with one lane, one slot and one element (`motionSeries()`) — no grid, no crossing or union groups. `normalizeTeamState` folds older saved data (a 徒手 cell anywhere, no `content`) into that shape, and the scoring side still handles a 徒手 in any position. A-side deductions are computed as six checks (`aDeductions`: つなぎ技3人以上 / 宙返り連続2人以上 / 組運動 / 全員同時タンブリング / 複雑な同調性タンブリング — 同一スロットで2〜4人が同時に転回系 / 後半シリーズの難度), and E is manual per-series plus whole-routine. **The values themselves are still provisional** — see the `※今後対応` note in `TeamScorer`; §3.4.5.4's 欠点テーブル is not implemented on the team side.

### Conventions and gotchas

- **Nothing can be manipulated while the apparatus is in the air** (`handsEmptyFlags`): between a 投げ and its キャッチ the hands are empty — always for a single-apparatus event (stick, rope), and for clubs/ring during a 二つ投げ — so a `skill` there cannot carry `hasApparatus`. The skill that *performs* the throw (`isThrow`) still holds it at take-off, so it may. The same flags drive all three paths: `stripForApparatus` clears the flag for scoring, `SeriesCard` omits the 手具操作 checkbox for those blocks, and `autoTemplate` passes every generated tumbling series through the strip. That made §3.5.5.5(3) reachable only through its second branch, so `computeScore` implements the rule as written — an E-difficulty 転回系 held with the apparatus earns +0.1 with **either** a throw during a held skill **or** two operations (`heldThrow || ops >= 2`) — and since those are two branches of one bonus, they never stack: `apparatusOpBonus` is a single 0.1 for the whole routine (`some(b => b.appOp > 0)`), like `seriesBonus` and `jumpVarietyBonus`, the other 最大0.10点 bonuses. The throw during an E tumbling no longer adds a separate per-row bonus (the original prototype's `E_BONUS` did, which double-counted the same rule), so a 後方宙返り半ひねり(操作)→前宙(操作)→きりもみ(視野外投げ)→キャッチ series scores D 0.9: tumbling E 0.7 + 手具操作加点 0.1 + 視野外の技術加点 0.1.
- **Input the current apparatus cannot express is never scored** (`apparatusBlockers` / `stripForApparatus` in `analysis.ts`): the apparatus buttons, a 他の手具 series template, an imported JSON and a share URL all leave the series items untouched, so a `useapp` throw/catch tag, a `twothrow`/`lefthand` reqType, `catchTwo` or a `ropeJump` can survive into an apparatus whose editor offers no such input — invisible on screen yet still worth 技術加点 or difficulty (a real stick routine carried a hidden 手具を使ったキャッチ worth +0.1, and a leftover rope jump is worth +0.3). `computeScore` strips those first (the same array comes back when there is nothing to strip, so the generator pays nothing), `IndividualScorer.changeApparatus` confirms and strips on an apparatus switch (naming what goes), and `loadSeriesTemplate`/`appendSeriesTemplate`/`loadRoutineTemplate`/`applyImportedData` strip silently. Add any new apparatus-specific input to both `apparatusBlockers` and `stripForApparatus` — and to `commonBlockers` (`templates.ts`), which is the same idea for 共通 templates.
- **`APPARATUS_REQUIRED_ELEMENTS` entries with an `auto` field are judged from the series input** (stick's 右投げ右受け, the 必須投げ of each apparatus, every apparatus's 転回系の投げ受け, and rope's four jump requirements — see `RequiredElementAuto`), not from the `apparatusElements` manual checkboxes — `computeScore` ignores the manual list for those, and `IndividualScorer` hides them from the checkbox card.
- **側転 is 徒手, not a 転回技** (`Skill.isHandElement`): it carries no `isConnectA`, so it never satisfies the つなぎ技 requirement, and `computeScore` skips it when collecting the 系統 for the 方向系 check — 側方系 is met by ロンダート or 側宙. It stays selectable as a 徒手動作 and still counts as one motion like the other A skills.
- **`connectNoApparatus` (つなぎ技のA難度に手具操作なし, −0.2) only looks at throw-free tumbling units** — a connect inside a 投げタン unit is not deducted.
- **§3.5.6.4 の欠点テーブル（芸術と多様性の主観評価）は手入力**：`ART_DEDUCTION_ITEMS` が表と1対1で、`computeScore(…, {artDeductions})` が項目ごとに `clampArtDeduction` で 0〜`max` に丸めて `artDeduction`/`artRows` を返し、A減点に加算する。「投げ受けの操作」だけは自動判定（投げ方・受け方の種類不足）なので手入力の対象外。
- **`computeScore` returns everything the UI needs**, including `seriesBreakdowns` (per-series contribution rows) and `required`/`missing` (必須要素 checks). Add new derived values to `ScoreResult`, not as ad-hoc calculations in components.
- **`seriesBreakdowns[i].tumRows`/`handRows`** carry one row per unit with `adopted`/`inTop` flags so `SeriesCard` can strike out what doesn't count; `tumDiff`/`handDiff` sum only the top-3-adopted units, so Σ per-series = `tumblingScore`/`handScore`.
- **Single source of truth for sums:** `computeScore` computes `seriesBreakdowns` first, then the literal-sum globals (`techniqueBonus`, `apparatusOpBonus`, `twoThrowMotionBonus`, and the base of `noApparatusDeduction`) are derived by summing those breakdowns — so per-series rows and grand totals cannot drift apart. Every unit is a difficulty candidate — a second, third… throw in one series is never suppressed, it just tends to lose the top-3 cut. **Identical content counts once for difficulty across the whole routine** (§3.4.4): every unit carries a `signature` (tumbling/投げタン = the sequence of non-A skills, so 手具を持っての前宙 and 投げての前宙 collide per Q&A Q22; hand = the composition of motions between throw and catch (type → count, order-insensitive); rope = jump id; technique tags and the presence of a throw are excluded), and among units sharing a signature only the highest-scoring one is adopted (ties keep the earlier) — but only for difficulty. Bonuses, throw counts, tumbling counts and every A-side check still see it, and `ScoreResult.unitAdopted[i][j]` tells the UI which units were skipped. Units in a `notDuplicate` series get a series-scoped key so they never collide with another series. The genuinely-global values that can't be derived per-series (top-3 adopted `tumblingScore`/`handScore`, the single `seriesBonus`, direction/throwCount/saltoChain/variety deductions) are computed across all series. When adding a rule, decide which category it is.
- **Duplicate-series suppression:** `seriesSignature` detects identical series (`dupSignatureFlags`); `Series.notDuplicate` lets the user declare "same input, different routine" (differences the input can't express — arm use in シェネ, motion breakdown) and clears the flag, giving the effective `dupFlags`. A duplicate contributes **nothing to D** (difficulty, series/technique/apparatus/two-throw bonuses all zero, and its units are excluded from the top-3 adopted pools) and nothing to counts; A-side checks (direction, salto chain, connect, required elements) still see its units. Per-series logic guarded by `if (isDup)`/`if (dupFlags[i])` — preserve that guard when adding rules, and use `dupSignatureFlags` (not `dupFlags`) for anything that must stay visible after the override.
- **`other` (その他) throws/catches count every time**, even in duplicate series — note the `throwOtherCount`/`catchOtherCount` paths sit *before* the `if (isDup) return` guard in the variety counting.
- State edits use `structuredClone` for immutable updates. Import/export (individual only) round-trips `SaveData` (`{ version: 1, apparatus, junior, series, executionDeduction, apparatusElements, violations, artDeductions }`) via file download and a copy/paste JSON modal (`JsonModal`). **`src/scoring/share.ts`** packs the same shape into a share URL (`buildShareUrl` with lz-string into the hash, `consumeShareHash` on startup in `App.tsx`) — team mode shares its own `{ kind: "team", team }` shape. Anything added to the save format needs to survive both paths.
- **Templates** (`src/scoring/templates.ts` + `TemplateModal`, individual mode): named 構成 (`Series[]`) and シリーズ (`Series`) templates kept in `localStorage` under `mens-rg-scorer:templates:v1`. Saving strips `executionDeduction` and loading preserves the target series' own value — a template is construction only. Same name = overwrite (`upsert`); the per-series dropdown splits them into 共通/この手具/他の手具 (`splitByApparatus`), and saving defaults to 共通 whenever the content allows it (`defaultTemplateApparatus`); `normalizeTemplateStore` drops broken entries so a bad store never breaks startup. Saving the current routine as a template does not require opening the manager — it sits both in the top toolbar and in the sticky bottom `.action-bar` (total score + 構成を保存 + テンプレート), so a long routine never has to be scrolled back up. Each series carries auto-derived **tags** (`SERIES_TAGS`/`seriesTags` in `analysis.ts`: 投げ / 投げタン / 三宙 (`maxSaltoChain >= 3`) / つなぎ) shown in the series header and on template cards, and the manager filters templates by free text, those tags, and difficulty/D-score **ranges** (`templateMetrics`). The manager shows templates as cards (name, apparatus, series count, and a `describeSeries` summary like 投げ→前宙→キャッチ); picking one edits it with the very same `SeriesListEditor`/`SeriesCard` the scoring screen uses (`showExec={false}`), so there is one editing UI, not two. Layout switches on `useNarrow()` (`matchMedia("(max-width: 900px)")`): wide screens get cards left / editor right, narrow screens show only the cards and overlay the editor as a sheet with a 一覧 back button.
- **`generate.ts`** builds a routine out of series templates: `generateRoutine(templates, {apparatus, junior, minScore, maxScore})` (and `generateForApparatus` when no apparatus is fixed) runs a randomized greedy over the usable templates (that apparatus + 共通), maximizing `-(out-of-range)*100 + dScore + aScore` — since missing required elements and junior over-throws land in the A deduction, that one number encodes "satisfy the requirements, push difficulty, stay in range" — then prunes any series whose removal doesn't lower the value, which is what keeps un-scored content (a 4th tumbling, a junior 6th throw, a duplicate series) out. 投げタン is capped at one per routine (`DEFAULT_MAX_THROW_TUMBLING`, overridable via `maxThrowTumbling`) — one satisfies the requirement, so extras carry the same penalty weight as falling outside the score range — Difficulty itself lowers a skill's pick weight (`SALTO_DIFFICULTY_WEIGHT`: D 0.6, E 0.3) because the harder a single skill is, the less often it appears; with that alone a max-D routine lands on 1〜2 D-or-above singles (the level a top Japanese routine actually carries), and `HIGH_DIFFICULTY_WEIGHT` (0.02) only breaks ties on top of it rather than capping anything. Ring is heavier and hard to twist while holding, so it gets fewer of those singles still: `APPARATUS_HIGH_DIFFICULTY_WEIGHT` (ring 0.4, via `apparatusHighDifficultyWeight`) multiplies the pick weight and divides the evaluation weight — measured, D-or-above singles average 1.24 (stick) / 0.96 (clubs) / 0.66 (ring) with the D score essentially unchanged. ハンドスプリング and 転宙 (`LIMITED_SKILLS`) are picked with a low weight and capped at `LIMITED_SKILL_MAX` (1) per routine, counting both skill and 徒手動作 entries (`limitedSkillCounts`), and タンブリング as a whole is capped at `DEFAULT_MAX_TUMBLINGS` (= `ADOPT_COUNT`, 3, counting the 投げタン, overridable via `maxTumblings`), since only the top three are ever scored. Packing 三宙 + つなぎ + 投げタン into three lines is tight for the greedy, so when the D target makes the 必須要素 mandatory and the best attempt still misses one, `swapIn` swaps single series against the remaining candidates (bounded rounds, only on the winning attempt, and it keeps the auto-series caps) before the result is returned; if a shortfall survives that, the generator rebuilds from a forced start — `satisfying` picks the candidates that cover the missing requirement and `greedyAttempt([t])` re-runs the greedy with that series pinned (up to `REBUILD_ATTEMPTS`, 5, per candidate, each followed by the same swap repair), which is what a routine sitting exactly at the D cap needs since covering the shortfall there means dropping a series, not adding one. How many throws a routine performs is shaped by the D target: `preferredThrowCount` is the mode (`THROW_COUNT_MODE_STEPS` — the rule minimum below D 2, 4 through the 2〜3 range, 5 from D 4, never below `throwCountRequired`), and `throwCountPenalty` pulls the count towards it — `THROW_COUNT_UNDER_WEIGHT` (0.1) per throw below it; above it the first extra throw costs `THROW_COUNT_OVER_WEIGHT` (0.12, or `THROW_COUNT_OVER_WEIGHT_HIGH` 0.2 from `THROW_COUNT_HIGH_SCORE` 5.0, where an added throw raises the score freely and the mode would otherwise slip to 6) and each further one `THROW_COUNT_FAR_OVER_WEIGHT` (0.3), because one throw over the mode is something a real routine does (a D 4-point routine may well perform 6) while two over is not (measured: D1.5 → 3 always, D2.5 → 4 at 80 %, D3.5 → 4 at 73 %, D4.5 → 5 at 70 % with 6 at 30 %, D5.2 → 5 at 60 % with 6 at 35 %). These weights are above the 0.1 difficulty step on purpose: 技術加点 has no cap, so without them the greedy keeps adding throws past what a real routine performs. The rule minimum itself is never traded away — `shortfallPenalty` charges `REQUIRED_ELEMENT_WEIGHT` for an unmet throw count whatever the D target, and `Evaluation.throwCountUnmet` makes the swap/rebuild repair run for it too, so a low D cap lowers difficulty rather than dropping a throw. Difficulty is only ever chased with the first four throws (the 投げタン plus `ADOPT_COUNT` hand units); beyond that a throw exists for 技術加点 alone, so `extraThrowOperation` × `EXTRA_THROW_OPERATION_WEIGHT` (0.01) keeps 徒手操作 out of the throws that difficulty never adopts. In a series with two 投げ受け the first is usually the harder one, so `reversedThrowOrderCount` × `THROW_ORDER_WEIGHT` (0.005) weakly disfavours the reverse — weakly, because real routines do it (the national rope routine opens 手以外の投げ→キャッチ→視野外の投げ→シェネ→キャッチ); 投げタン units are excluded since their difficulty comes from the tumbling. Repeating the same salto across the routine costs `SALTO_VARIETY_WEIGHT` (0.02) per extra occurrence (`saltoRepeatCount`; 前宙 is exempt via `REPEATABLE_SALTOS`) — below the 0.1 difficulty step, so variety only breaks ties and never trades away real points. Whether the 必須要素 are optional or mandatory depends on the D target: `requiresAllElements` is true when no upper bound is set or it is at least `REQUIRE_ALL_ELEMENTS_MIN_SCORE` (3.0), and `requireAllElements` overrides it either way, and each unmet requirement then costs `REQUIRED_ELEMENT_WEIGHT` (10) — enough to outrank any difficulty gain, but below the out-of-range penalty (×100) so the range still wins. `shortfallPenalty` is what counts them, and it also adds `A_PRIORITY` × `A_PRIORITY_WEIGHT` (0.01, below the 0.1 difficulty step) so that when they cannot all be met the ones that go are the ones a real routine gives up last: 投げの回数 = 各手具の必須投げ受け ＞ 投げタン ＞ D難度 (the `dScore` term itself) ＞ 多様な投げ受け ＞ つなぎ ＞ 三宙 ＞ つなぎの手具操作. Everything else in the evaluation is a straight D-vs-A comparison — `dScore + aScore`, same weight — so a series is taken only when the difficulty it adds beats the A deductions it brings (a 手具操作なし tumbling costs 0.2, a junior 6th throw 0.3, and so on); measured, the mandatory-elements rule costs about 0.07 of D+A on average, i.e. the comparison would usually pick the same routine anyway. Below that the shortfall is only the A deduction it already is, because a gymnast scoring 0〜1点台 genuinely does not meet them (the measured floor for a fully-compliant routine is about D 2.0). The greedy looks at the user's own templates first and fills what is missing from the auto candidates (`autoThrows.ts` / `autoTumblings.ts`), and `AUTO_SERIES_WEIGHT` (0.02, same idea as the variety weight) makes it prefer a template over an auto series on a tie. Series order is not left to the greedy: `orderSeries` splits the chosen series into 転回系を含むもの (a tumbling unit or a 投げタン) and 投げ・徒手だけのもの and `interleave`s them so the routine alternates the way a real one does, keeping the greedy order only if the interleaved one scores worse (ordering is score-neutral except for junior's throw cap, which counts from the front). `GenerateModal` drives it.
- **`autoThrows.ts`** — the 投げ series the generator builds itself, so templates don't have to cover every 投げ方. `AUTO_THROW_PATTERNS` holds the shapes (投げ→1〜2回シェネ→前転→転がり→キャッチ / 投げ→1〜3回シェネ→前転→キャッチ / 投げ→3〜4回シェネ→キャッチ, the last two also with a 視野外投げ→視野外キャッチ pair appended, plus 投げ→前転3回→キャッチ — no シェネ, and 縦3動作 makes it E — plus the three minimal ones, 投げ→シェネ→キャッチ / 投げ→前転→キャッチ / 投げ→キャッチ (徒手0〜1動作), which are how an apparatus's 必須投げ (左手投げ / 二つ投げ) is most often satisfied with the least operation; being cheap they show up more as the D target drops, but they are not a low-level-only thing — and two `leadPair` shapes that put a bare 投げ→キャッチ *in front* of the main throw, which buys one more throw style with no extra operation the way the national rope routine opens 手以外の投げ→キャッチ→視野外の投げ→シェネ→キャッチ; the lead throw style is dealt as `leadThrowStyle` (its catch is a plain one, and 二つ投げ is never the lead since it needs a 2つ同時キャッチ)). `autoThrowSpecs(apparatus)` crosses every shape with every throw style the apparatus allows (`autoThrowStyles`: 通常 / 左手投げ or 二つ投げ / 視野外 / 手以外 / その他 / 手具を使った投げ) and deals out the catch style (`autoCatchStyles`: 通常 / 視野外 / 手以外 / その他 / 手具で押さえつけて — the last one clubs・ring only), the シェネの手 (手なし plus each `HANDS_TYPES`, only for shapes that have シェネ) and the シェネの回数 round-robin (`cycler` reshuffles each lap), so candidates repeat as little as possible. `catchStylesForThrow` drops 手具で押さえつけてキャッチ from a 二つ投げ candidate — both apparatus are in the air, so there is none left in hand to press with — The 縦3動作 shape (投げ→前転3回→キャッチ, `verticalThree`) is normally received by pressing the other apparatus against it, so its catch style is drawn weighted (`VERTICAL_THREE_OTHER_CATCH_WEIGHT`, 0.2 for anything but 手具を使ったキャッチ) and `generate.ts` charges `VERTICAL_THREE_THROW_WEIGHT` (0.85 per series — more than the shape can add, so it only appears when the score genuinely needs it) for a 縦3動作 throw caught any other way (`verticalThreeThrowCount`) — so it only appears when the D range genuinely needs it (measured: 0〜1 per 20 routines with no range, but 9 of 10 once a 4.5 minimum makes it necessary). `catchStyleWeight` also makes a 視野外のキャッチ off a 左手投げ rare (`LEFT_HAND_NO_VIEW_CATCH_WEIGHT`, 0.1). Two throws inside one series constrain each other, so `catchStylesForPattern` drops 視野外のキャッチ and 手以外のキャッチ from the shapes that append a second 投げ受け (catching out of sight then throwing out of sight cannot physically be done, and neither can throwing again straight out of a non-hand catch), and `throwStylesForPattern` drops 手以外の投げ from the `leadPair` shapes, whose main throw is the *second* one — the lead throw itself may be 手以外, which is how the national rope routine opens. `buildAutoThrowSeries` turns a spec into a `Series` — 二つ投げ is received with `catchTwo` so `checkApparatusFlow` stays clean — and `autoThrowTemplates` wraps them as `SeriesTemplate`s flagged `auto: true` (never saved to `localStorage`). Their names are just the kind (自動生成の投げ / 自動生成のタンブリング / 自動生成の投げタン) — the series content is shown next to the name, so the name carries no description. Each candidate keeps its `spec`, so `generateRoutine` can retune it: between the greedy add and the prune, `tuneAutoThrows` walks the chosen auto series and moves each one's シェネ回数 within its pattern's `cheneCountRange` while the evaluation improves — so a D-score cap is met by shortening a series rather than dropping it whole (and a lower bound by lengthening one). `generateRoutine` appends them to the pool but keeps at most `DEFAULT_MAX_AUTO_THROWS` (3) per routine — 技術加点 has no cap, so otherwise they would crowd out the templates — and only where they raise the evaluation, so a routine need not contain any. `autoThrows: false` turns them off (the GenerateModal checkbox, and generator tests that want a fixed pool). A user template for the apparatus is still required: with none, `generateRoutine` returns null rather than building a routine of throws alone.
- **`autoTumblings.ts`** — the タンブリング the generator builds itself, so templates don't have to enumerate every combination of the skills a gymnast can do. Two layers decide what is valid. **The editor's input constraints**: `needsRoundoffBefore` (a 後方系 needs a ロンダート in front unless the previous skill lands backward — the builder splices one in exactly like `SeriesListEditor` does) and the picker's own `skillOptions(junior, skillFlowAfter(prev))`, which `tumblingFlowErrors(series, junior)` re-checks each built series against (asking the picker rather than copying its logic, so it follows constraint changes). **And how routines are actually built**, which is what shapes a chain: `nextSaltoOptions(prev)` takes the 系統 from the previous skill's landing (`leadsBackward` → 後方系, otherwise 前方系/側方系) and caps difficulty at the previous skill's, since a chain steps *down* (後方1回半ひねり→前方1回ひねり→前宙); テンポ宙返り/テンポひねり (`TEMPO_SKILLS`) are the exception that may go up, and are the only 後方系 a chain continues past into another 後方系 — plain 後方系 chains are rare, so they stop; a **forward** salto that lands backward (前宙半ひねり) does continue into 後方系, which is how a real 三宙 like ロンダート→後方1回半ひねり→前宙半ひねり→ダイビング前宙 is built. The other exception is a 後方伸身宙返り (`isBackLayoutSalto`, twists included): it lands backward but is normally followed by 前宙・きりもみ・きりもみ転回 (`AFTER_BACK_LAYOUT_SALTOS`, 側宙 coming after that 前宙), so that list is returned as-is — きりもみ系 only count as saltos inside a chain (Q&A Q7), which is exactly this position, so no difficulty ceiling applies — and it carries weights (`saltoWeights`) because the real split is 前宙 ＞ きりもみ ＞＞ きりもみ転回. `CHAIN_END_SKILLS` (とび前転・きりもみ — they land on the neck and back — plus きりもみ転回 and 側宙, which in practice only ever come last) end a chain: `nextSaltoOptions`/`connectOptionsAfter` return nothing after them and none of them is used as an entry or a つなぎ. 側転 is 徒手 now, so it is not a つなぎ either (it stays as the lead-in to a 側宙). `connectOptionsAfter(prev)` allows つなぎ技 only where they happen: ロンダート/側転/ハンドスプリング/とび前転 after a forward-landing salto, バク転 only after テンポ; `saltoOptionsAfterConnect` then picks from the 系統 that connect leads into, with `CONNECT_FINISH_RARE` (ただの後方宙返り) down-weighted rather than banned — advanced gymnasts finish a つなぎ with ダイビング前宙/後方伸身宙返り when they want a B, but a junior or a gymnast whose D sits in the 0〜1点台 does perform it. A 投げタン that throws first never starts with a ロンダート — apparatus air time only allows 前方系, finished with 前転 (`THROW_ROLL_MOTION`) or 側宙/転宙 (`THROW_FINISH_SALTOS`); throwing during the last salto instead (`throwInSkill`) has no such limit, since the air time only covers what follows the throw. A chain steps down in difficulty, with one named exception: `DIFFICULTY_RISE_AFTER` lets 後方宙返り半ひねり continue into the harder 前方宙返り1回ひねり (and on into a 前宙) because gymnasts do perform that, weighted down to `DIFFICULTY_RISE_WEIGHT` (0.3) since going up is otherwise rare. Under junior rules a low D target prefers the skills junior upgrades — `withJuniorBoost` multiplies ダイビング前宙 / 後方宙返り半ひねり / 後方伸身宙返り半ひねり (`JUNIOR_SKILL_DIFFICULTY`, all C for junior) by `JUNIOR_UPGRADE_BOOST` (2) while the target is under `JUNIOR_UPGRADE_BOOST_MAX_SCORE` (3.0). Skills of the same difficulty are not performed equally often, so `SKILL_PICK_WEIGHT` multiplies the pick weight: ロンダート ＞ バク転 ＞ ハンドスプリング (entries and つなぎ), 前方宙返り1回ひねり ＞ 伸身前宙 ＞ きりもみ転回, 側宙 ＞ 転宙, 抱え込み = 伸身 ＞ 屈伸, 前宙 ＞ 前宙半ひねり, and テンポひねり lowest of the backward C skills except the 屈伸 ones, which stay below it (ハンドスプリング and 転宙 are already at 0.2 through `LIMITED_SKILLS`), and `CONNECT_RISE_WEIGHT` (0.3) down-weights a つなぎ finish harder than the salto before it, since a chain steps down even across a connect (E is C→B→B, not B→C→B). After a テンポひねり the next skill is テンポ宙返り ＞ any other salto ＞ バク転: `AFTER_TEMPO_TWIST_WEIGHT` (3) boosts テンポ宙返り in `saltoWeights`, and `TEMPO_CONNECT_WEIGHT` (0.3) down-weights テンポ系 as the first salto of a つなぎ candidate, since a テンポ is the only place `connectOptionsAfter` offers バク転. A salto that lands facing backward — a backward salto with a whole-number twist, or a forward one with a half twist (`endsFacingBackward`) — is not where a line stops: `canEndChain` keeps it out of the last position. Ending on the **backward** one is something a low-scoring gymnast does, so it is drawn with `backwardEndChance` — halving per point of the D target and exactly 0 from `BACKWARD_END_ZERO_SCORE` (3.0, the level where a routine starts carrying chains in several series, same threshold as `REQUIRE_ALL_ELEMENTS_MIN_SCORE`) or with no cap at all (measured: 8 % of lines at a 1.5 target, 10 % at 2.0, 0 % from 2.5 up); the draw is stored on the spec (`allowBackwardEnd`) so `withSaltoCount` tunes within the same decision. 後方宙返り半ひねり lands forward, so nothing stops a chain from stopping there, but an advanced gymnast almost always continues into a 前宙 or 側宙 — `RARE_CHAIN_END_SKILLS` with `RARE_CHAIN_END_CHANCE` (0.1, and `basicLevel` always allowed) makes the builder extend the chain by one salto instead, dropping the candidate when it cannot continue (measured: 0 of 75 advanced lines end there, 側宙 24 and 前宙 18 lead instead). Ending on a **forward half twist** (前宙半ひねり, 前方1回半ひねり) never happens in competition, so it is excluded regardless of the draw, and a 2回宙返り is exempt from all of this since it neither continues nor connects. Since nothing may follow a backward-landing salto either, those skills simply drop out of advanced chains. Throwing during a 側宙 is rarer still — practice footage with clubs exists but no competition record — so `THROW_IN_SIDE_SALTO_WEIGHT` (0.1) down-weights 側宙 as the throwing salto of a `throwInSkill` chain. `NO_ROLL_AFTER_SKILLS` (側宙) plus `endsFacingBackward` drop the closing 前転 of a `rollFinish` shape — nothing physically stops it, but nobody rolls out of a 側宙, so the throw is simply caught. バク転 is never used as an **entry** (`TUMBLING_ENTRIES` backward is ロンダート alone) — adding one changes neither difficulty nor any requirement (only 宙返り−A−宙返り counts as a つなぎ), so it needs a reason to be there. Among shapes that reach the **same** difficulty there is still an order of how often they are actually performed — `TUMBLING_SHAPE_ORDER` plus `readTumblingShape`/`tumblingShapeRank`/`throwTumblingShapeRank` rank them (E: C→B→B ＞ D→B = C→C ＞ C→C→B ＞ B→B→B→B ＞ anything else ＞ a single E; D: C→B = B→B→B ＞ else ＞ a single D; 投げタン E: C＋側宙 = D＋前転 ＞ a つなぎ chain throwing on the last B ＞ a plain chain throwing on the last ＞ C plus a non-側宙 salto ＞ else ＞ a single E; 投げタン D: 前方C＋前転 = 前方B＋側宙/転宙 ＞ throwing inside a C series ＞ else), and `generate.ts` subtracts `shapeRankTotal` × `SHAPE_PRIORITY_WEIGHT` (0.005 per rank, so 3 tumblings at the worst rank stay under the 0.1 difficulty step — it only decides between equal-scoring routines). Nobody throws at the transition from a backward-landing salto into a forward one (`isBackToForwardThrow`), so those candidates are dropped — except きりもみ with a 視野外投げ, which is physically fine and looks good: `BACK_TO_FORWARD_THROW_CHANCE` (0.15) keeps it occasionally and `throwInSkillTypes` tags the throw 視野外. Half-twist backward saltos land forward, so 後方伸身宙返り1回半ひねり→前宙 with a throw is outside this rule and stays. A 投げタン can also be followed by a second 投げ受け inside the same series (`secondThrow`, dealt from `secondThrowStyles` — 手以外 is never the second throw, while stick's 左手投げ and clubs/ring's 二つ投げ are fine since the apparatus is back in hand); throwing before the salto makes that continuation more likely than throwing during it (`PAIR_AFTER_THROW_FIRST_CHANCE` 0.5 vs `PAIR_AFTER_THROW_IN_SKILL_CHANCE` 0.2, via `pairAfterChance`). `AUTO_TUMBLING_PATTERNS` holds the five shapes (連続1〜3本 / つなぎ技入り / 投げ受け＋前転 / 投げ受け＋側宙 / `throwInSkill`: a 2〜3-salto chain whose **last** salto carries the throw, finished 前転→キャッチ — the air time only constrains what comes after the throw, so the entry ロンダート and the chain in front are free, and one series then satisfies both 三宙 and 投げタン, which is how the national clubs routine does it: ロンダート→後方伸身2回半ひねり→前宙(投げ)→前転→キャッチ). **The vocabulary is the user's**: `generateRoutine` passes `usedSkillIds(own templates)` as `skillIds`, so the chains only combine skills the templates already show (a shape with no usable skill is skipped, not invented); with no templates at all the full skill list is used, which is what lets a routine be generated from nothing. Candidates carry their `spec` like the throws, so `tuneAutoSeries` can raise or lower a chain's 宙返りの本数 (`saltoCountRange` / `withSaltoCount`) to meet a D-score range, and at most `DEFAULT_MAX_AUTO_TUMBLINGS` (4 — three for the difficulty top-3 plus one that may carry a required element) go into a routine. A D target below `BASIC_LEVEL_MAX_SCORE` (2.0 — a gymnast scoring 0〜1点台) switches the candidates to `basicLevel`: what those routines actually look like is ロンダート→宙返り1本で終わり, no 三宙 (`BASIC_LEVEL_MAX_SALTOS` = 2), no つなぎ, and nothing above C (`BASIC_LEVEL_MAX_DIFF`), so the generator stops proposing a 2回半ひねり just because the total lands in range. `autoTumblings: false` turns them off.
- A template's apparatus can be **共通** (`COMMON_APPARATUS`): usable with every apparatus, allowed only when the series has no apparatus-specific input (`commonBlockers` — 二つ投げ/左手投げ/手具を使った投げ・キャッチ/2つ同時キャッチ/ロープ跳び); such templates are edited with those inputs hidden (`SeriesCard`'s `common` prop) and scored as stick (`scoringApparatus`).
- Team mode (団体モード) is fully wired for D/A/E, but the A-side deduction values are provisional (see `team.ts`) and §3.4.5.4 の欠点テーブル is individual-only so far; crossing-group detail and union-skill difficulty are still TODO.
