# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Vite + React + TypeScript single-page app that calculates competition scores for Japanese **men's rhythmic gymnastics** (男子新体操) — 個人 (individual) and 団体 (team, 5-person) modes. The UI language is Japanese; domain terms below keep the Japanese names since they appear throughout the code.

Two rule documents live at the repo root — keep both and `src/scoring/constants.ts` in sync:
- **`mens-rg-rules.md`** — official scoring rules (2025 edition) translated from the PDF. Pure rules, no code references.
- **`app-scoring-spec.md`** — maps rules to app code: constant names, pipeline description, implementation status, TODOs.

## Commands

- `npm run dev` — Vite dev server (hot reload).
- `npm run build` — `tsc -b` typecheck (strict) then `vite build` to `dist/`.
- `npm run typecheck` — types only, no emit.
- `npm run preview` — serve the production build locally.
- `npm test` — vitest (single run); `npm run test:watch` to keep it running.
- `npm run probe -- "<技名 or 前宙→きりもみ転回>" [--apparatus clubs] [--max 3.5,none] [--min 4] [--rarity 0,50,100] [-n 12] [--junior] [--future F]` — 「○○は生成される？」を一度に確かめる（`src/scoring/probe.ts`、`scripts/probe.mjs`）。候補（`autoPool`＋本数違い）に当たる数と、実際に生成した構成に出た数、その技が各上限で候補に入れるか（`usableSkills`）を表で出し、「候補にない」か「候補にはあるが評価で負けている」かを切り分ける。生成に形を足してもこのコマンドは変えなくてよい（`autoPool` と `generateRoutine` を呼ぶだけ）。シリーズごと指定するなら `--exact`（`*` は任意の1アイテム）。`--seed` で再現できる。

The scoring logic is covered by vitest suites in `src/scoring/__tests__/` (analysis / score / aside / team / junior / templates / generate / tags / options / twist ほか). **After changing scoring logic, add or update a test there and run `npm test` plus `npm run build`.** `test-reports/` holds the reports written by the `scoring-test` skill (`.claude/skills/scoring-test`), which walks one rule-compliance pass: compare `mens-rg-rules.md` against `src/scoring/`, add tests for an angle no past report covered, and file an issue for anything wrong.

## Architecture

The codebase splits cleanly into **pure scoring logic** (`src/scoring/`) and **UI** (`src/App.tsx` + `src/components/`). The UI holds state and renders; it contains no scoring math.

`App.tsx` is a thin shell holding a `mode` toggle and rendering either `IndividualScorer` (個人) or `TeamScorer` (団体, 5-person). Each scorer owns its own state. Styling is a **glassmorphism design system in `src/index.css`** (CSS custom properties + class names + hover/transition states) — components use `className`, not inline styles. Change visual tokens in the `:root` block. Every モーダル shares one `.modal-overlay` (`z-index: 1000`), so a modal opened **from inside another** needs `.modal-overlay.is-nested` (1100) or it renders behind and cannot be clicked — `SkillWeightModal`, opened from `GenerateModal`, is the one case (and it is rendered after the outer overlay so the DOM order matches too). Series input (`.skill-row`/`.skill-block`) is a horizontal flow on wide screens and **stacks vertically at ≤720px** (the `.arrow` connector rotates to point down), so phones never scroll sideways. Each item block ends with an `.item-actions` row — `.move-btn` arrows at both ends swap the item with its neighbour (`SeriesListEditor`'s `moveItem`, disabled at the ends; the arrows rotate to ↑↓ in the stacked layout) and the ✕ in the middle removes it.

The data model is a flat **list of `Series`**, each an ordered list of `items` (`src/scoring/types.ts`). Everything else is derived. Five item `kind`s (a discriminated union on `kind`):

- `throw` (投げ) / `catch` (キャッチ) — bracket an apparatus throw; `reqTypes` holds required throws (e.g. `twothrow`, `lefthand`), `throwTypes`/`catchTypes` hold optional technique tags.
- `skill` (タンブリング技) — a tumbling element referencing `SKILL_LIST` by `skillId`, with `hasApparatus`, `isThrow` (throw executed mid-skill) and `isCatch` (**catch** executed mid-skill) flags. **`isCatch` is scored exactly like `isThrow`**: `isCatchItem`/`catchTagsOf`/`caughtCount` (`analysis.ts`) are what every path reads, so the skill closes its unit the way a `catch` item does (the series becomes a 投げタン), its `catchTypes` count toward 技術加点 and 多様な受け方, its `catchTwo` is offered exactly where a catch item's is (`catchTwoFlags`), and `apparatusBlockers`/`stripForApparatus`/`commonBlockers` gate those tags per apparatus. **One difference from a `catch` item: the unit is not closed when a 転回技 follows immediately** (`catchSkillContinues`) — the catching skill is mid-line, so 投げ→ロンダート(受)→後方宙返り1回半ひねり→ロンダート→ダイビング前宙 (a real ring routine) is **one 投げタン** rather than a lone-ロンダート 徒手 unit (a single A-difficulty skill counts as one 徒手動作, so splitting it would not even satisfy 転回系の投げ受け). A 徒手 or a 側転 after the catch still splits, and a `catch` item always splits — the hands take the apparatus back there and the next line starts separately. The one asymmetry is 手具操作: the throwing skill holds the apparatus until it releases, so it may carry one, while the catching skill only gets it back at the very end, so `handsEmptyFlags` reports its hands empty and the editor hides the checkbox. 投げ and 受け are mutually exclusive on one skill (`SeriesCard` disables whichever is off while the other is on, never the one that is on). Saltos can also be entered **parametrically** — base (後方宙返り/前宙) × ひねり回数 × 姿勢 (抱え込み/屈伸/伸身) — and the picker switches between the flat list and that builder (a 手動入力／一覧入力 button per block). `buildTwistSkillId` returns the existing `SKILL_LIST` id whenever the combination has one, so dedup signatures never split; only combinations missing from the list become a synthesized `tw:<base>:<twist>:<posture>` id, which `skillDef()` resolves into a full `Skill` via `twistName`/`twistDifficulty`. Difficulty follows §3.6.2: backward depends on twists alone, forward is one step higher for 伸身 (`twistDifficulty`). The list/builder choice is **per skill block** and defaults to the list (switching one leaves the other blocks alone, and nothing is remembered across blocks or reloads); only a synthesized `tw:` id opens in the builder, since the list can't edit it.
- `ropeJump` (ロープ跳び, rope only) — **シリーズの中ではなく、徒手・構成タブの跳びシリーズ（`SaveData.ropeJumps: RopeJumpItem[][]`、`RopeJumpList`）で入力する**。跳びは演技の要所ごとに実施するので、跳びシリーズを分けて入力し、**連続かどうかは「同じ跳びシリーズの中で隣り合うか」だけで決まる**。選択肢は「何重跳びか × 前／後ろ」（`ROPE_JUMPS`）だけで、`cross`（クロス、2重・3重だけ表示）と `count`（跳んだ回数、未指定＝1、`motion` と同じ入力欄）は別の入力。難度は `ropeJumpDifficulty(resolveRopeJump(item))` が §3.5.5.3 の表から引く（3重2回・3回以上・4重連続2回以上は回数で表す）。跳びは**1つごとに評価**され（`ropeJumpRows`）、投げ受けの徒手ユニット・単独の徒手系要素と**同じ上位3つの枠**を争う（同じ跳び＝`ropeJumpKey` は1回だけ）。**Σ`seriesBreakdowns[i].handDiff` ＋ `handElementScore` ＋ `ropeJumpScore` ＝ `handScore`**。ロープの4つの自動判定と様々な跳び加点は、**同じ跳びシリーズで隣り合う跳びの回数の合計**で「連続」を見る（間に移動しない跳びなどが入る・跳びシリーズが分かれていると途切れる。前2重→前3重は、同じ跳びシリーズならその場の前回し連続2回を満たす）。難度の重複と上位3つは跳びシリーズをまたいで全体で数える（`ropeJumpRows[].group/index` が画面の行に対応）。旧データの id（`3bc`・`3x2f` など）は `LEGACY_ROPE_JUMPS` で今の表現に解決し、旧データでシリーズの中に入っていた `ropeJump` アイテムは `hoistRopeJumps` が元のシリーズごとに1つの跳びシリーズへ移し、跳びシリーズに分ける前の保存形式（跳びを1本に並べた配列）は `normalizeRopeJumps` が1つの跳びシリーズとして読む（`computeScore`・`normalizeIndividualDraft`・インポート・テンプレート読み込み）。ロープ以外では跳びシリーズごと採点しない。
- `motion` (徒手動作) — empty-hand body motions referencing `MOTION_OPTIONS` (`HAND_MOTIONS` plus the 転回技 that can count as 徒手 — 側転/バク転/きりもみ etc.; `motionDef()` resolves either). Each carries a repeat `count` (blank in the UI = 0, and a 0-count motion is counted nowhere — see `motionTimes`) and, for シェネ, a `hands` flag plus a `handsType` (片手上げ/両手上げ/回旋/その他) — hands/no-hands and each hands type are different techniques (Q&A Q28), a unit mixing them gets one signature per variant so it collides with any of them (Q&A Q21), and その他 sets `Unit.neverDuplicate` so it never counts as a duplicate.

### The scoring pipeline (`src/scoring/`)

- **`constants.ts`** — all definition tables and tunable rule values (`SKILL_LIST`, `HAND_MOTIONS`, `DIFF_SCORE`, `*_BONUS`, `*_DEDUCTION`, `*_CAP`, `ADOPT_COUNT`, …). Change scoring values **here only**. Dropdown grouping lives here too: `skillOptionGroups(junior, flow)` splits tumbling skills into 前方系/側方系/後方系 (`SKILL_CATEGORY_ORDER`) and `motionOptionGroupsFor(prevMotionId)` splits 徒手動作 into 縦回転/横回転 (`MOTION_AXIS_GROUPS`; every 転回技 used as 徒手 is vertical) — both keep the existing within-group ordering, and the pickers render them as `optgroup`s.
- **Which 系統 can follow which (input aid, no score effect)** — `leadsBackward(prevSkillId)` (`constants.ts`) answers "does this skill finish facing backward": true for `BACKWARD_ENTRY_SKILLS` (ロンダート/バク転), for backward saltos with whole-number twists, and for **forward saltos with a half twist** (前宙半ひねり — you land facing back, so 後方系 can follow directly); false for backward half-twists (`twist % 1 !== 0`) and `FORWARD_LANDING_BACK_SALTOS` (ダイビング前宙). It only decides whether a ロンダート is needed, not what is offered: the **only** place the picker narrows is right after a ロンダート/バク転, where 後方系 is the sole group (`skillFlowAfter(prevSkillId)` returns the `SkillFlow` — `backward`/`forward`/`side` — that `skillOptions`/`skillOptionGroups` filter by, and a skill that's already selected stays in the dropdown as its own option). Everywhere else all three groups stay selectable — going back to 前方系 after a salto is impractical but possible — and when 後方系 is picked where `leadsBackward` is false the editor **inserts a ロンダート**: `needsRoundoffBefore(items, iIdx)` (`analysis.ts`) tells `SeriesListEditor.updateItem` to splice a `roundoffItem()` in front (a standing バク転 with nothing before it is left alone). Team mode reuses `skillFlowAfter` for the same filter but does not auto-insert (the lane is a fixed grid of slots).
- **`analysis.ts`** — per-series functions. `analyzeSeries(series)` is the heart: it walks `items` left-to-right and flushes a buffer into **units** whenever a `catch` is seen, and also at a 徒手 element that sits *between* tumbling skills (`unitSplitFlags`) — 前宙→前転→前宙 is three units (tumbling / hand / tumbling), each judged on its own, and the salto chain breaks there too. A 徒手 with no 転回技 on one side (the 前転 you land a 投げタン with) does not split, and **nothing splits while a throw is in the air**: between 投げ and キャッチ a mix of 徒手 and タンブリング keeps its existing judging as one chunk.
  - A run with **no throw** → a `tumbling` unit; `calcTumblingDifficulty` = first skill's value, +1 per additional non-A skill, +1 if any throw, capped at E.
  - A run **containing a throw** → a `throw` unit; difficulty is `max(handDiff, tumblingDiff)`. `calcHandDifficulty` derives hand difficulty from accumulated motion count (縦3動作 → forced E). A throw unit that also contains a skill is a **投げタン** (`isThrowTumbling`) and counts toward tumbling, not hand.
  - Also: `saltoFlags` (きりもみ/きりもみ転回 count as saltos only inside a salto chain — Q&A Q7 — and every salto test goes through it), `tumblingFlags`/`handMotionsOfSkill` (a skill that isn't 転回系 — an A skill outside a つなぎ, a standalone きりもみ — counts as 徒手 motions instead: A/きりもみ = 1, きりもみ転回 = 2, summed with the `motion` items; a unit with no 転回系 skill becomes a hand unit even without a throw), `maxSaltoChain`, `hasConnect`/`hasConnectWithoutApparatus` (つなぎ技 detection), `checkApparatusFlow` (in-hand/in-air validator, warnings only — no score effect), `seriesSignature` (dup detection).
- **十年後モード（F・G難度）** — a speculative mode the rules do not have: `FutureLevel` (`"F"` / `"G"` / `null`) raises the difficulty ceiling above E, with `DIFF_SCORE` F 0.9 / G 1.1. Only the **ceiling** changes — every place that used to stop at E goes through `maxDiff(future)` / `clampDifficulty(value, future)` (`twistDiffValue` extends the §3.6.2 step table to 4〜5 twists, `calcTumblingDifficulty`, `calcHandDifficulty`, team's `chainValue` / 5-person bump / crossing), while bonuses, deductions, required elements and dedup stay exactly as they are. `SKILL_LIST` entries flagged `future` are hidden unless the mode is on and their difficulty fits the chosen ceiling, and those flagged `teamOnly` (the mode's 2回宙返り系 — ルドルフハーフ / 後方伸身2回宙返り1回ひねり / リジョンソン, which individuals don't perform) only reach the team picker (`skillAllowed(id, junior, future, team)`; `skillBlockedReason` names why a skill is absent). Hand units reach F/G by a **weighted motion count** instead of a plain one (`HAND_MOTION_WEIGHT` / `futureHandValue`: 縦回転 — 前転・後転・徒手扱いの転回技 — costs 1.5 against 横回転's 1, because it eats more of the apparatus's air time; F from 5.0, G from 5.5), so シェネ×5 is F while シェネ×4→前転, 前転×4 and any 6 motions are G. That also made 縦3動作's E a **floor rather than an override** (`Math.max`), since the early `return "E"` had 縦3動作＋シェネ3回 scoring below a plain 6 motions once the ceiling rose. An existing skill can also be re-rated by the mode — `FUTURE_SKILL_DIFFICULTY` lifts ルドルフ from E to F, the same shape as `JUNIOR_SKILL_DIFFICULTY` — and `skillDifficulty(id, junior, future)` clamps to the ceiling so **turning the mode off never leaves an F skill scoring 0.9** (`skillDef` keeps the raw definition). The flag is threaded exactly like `junior` (`computeScore(…, {future})` → `analyzeSeries` → …, `TeamState.future`, `GenerateOptions.future`), and the generator treats the F/G skills as the one exception to "the vocabulary is the user's" (`usableSkills` in `tumblingTransitions.ts`) — nobody performs them yet, so they join the candidate pool even when no template shows them; with the mode off they are not in the transition table at all. The throw side gets its own future-only shapes (`AutoThrowPattern.future` / `throwPatternAllowed`: シェネ×5 for F, シェネ×6 / シェネ×4→前転 / 前転×4 for G), since the current shapes stop at 4 motions. The toggle plus its F/G dropdown is **hidden until the junior toggle is flipped `FUTURE_UNLOCK_TOGGLES` (10) times** (`useFutureUnlock`, remembered per device in `localStorage`, shared by both modes).
- **`score.ts`** — `computeScore(series, apparatus, opts): ScoreResult` is the single source of truth for the whole-routine **individual** score. `opts.junior` switches to the ジュニア適用規則 (§10 変更規則1): ダイビング前宙/後方宙返り半ひねり/後方伸身宙返り半ひねり are C instead of B (`JUNIOR_SKILL_DIFFICULTY`, read via `skillDifficulty(id, junior)`), the minimum throw count drops from 3 to 2 (`throwCountRequired(junior)`), 2回宙返り系 are hidden from the skill picker (`Skill.isDoubleSalto` / `skillOptions(junior)`), and throws are capped at 5 (`throwCountMax(junior)`) — the 6th onward count for nothing (difficulty, throw count, variety, required throws, technique bonus) and cost −0.3 each. The flag is threaded down to `analyzeSeries` / `calcTumblingDifficulty` and defaults to `false`. **Team mode has junior too**: the flag lives in `TeamState.junior` (round-trips through `normalizeTeamState`) and `computeTeamScore` passes it to `analyzeTeamSeries` / `calcChunkDifficulty` / the bonuses — same per-skill difficulties and double-salto ban, plus `JUNIOR_SKILL_COMBOS` (`juniorComboAt`), which judges バク転→後方伸身宙返り as a single C and takes the max against the plain chain and the 5-person bump. Junior also caps each series' execution deduction at 1.0 (`JUNIOR_SERIES_EXECUTION_MAX` via `clampSeriesExecution`) — **team only**; individual series and both modes' whole-routine deductions are uncapped. The UI calls it once (memoized) and renders the returned object. Final score = **D (難度, additive) + A (10 − deductions) + E (10 − manual execution deductions)**, both A and E floored at 0.
- **`team.ts`** — the 団体 (5-person) model and `computeTeamScore(team): TeamScoreResult`. Different data shape: a grid of `Series` × player `lanes` × `slots` of `Cell`s; horizontally-adjacent non-empty cells form a **chunk** whose difficulty reuses `SKILL_LIST`/`DIFF_*` (no throw +1, unlike individual). Team 徒手 is a different thing from individual 徒手: there is no apparatus, so the motion-count options are gone — a `motion` cell picks from the §3.6.1 table (`HAND_ELEMENTS`, 跳躍/バランス/倒立/柔軟) and scores its **団体 (5名実施)** value (`teamHandDifficulty`), never chains with neighbouring cells, and is not bumped by the 5-person rule. 徒手 also presumes all five members perform it, so it is a property of the series, not of a cell: `TeamSeries.content` is `"skill"` (転回 grid) or `"motion"`, toggled next to the 同時実施シリーズ button, and a 徒手 series is `mode: "allTogether"` with one lane, one slot and one element (`motionSeries()`) — no grid, no crossing or union groups. `normalizeTeamState` folds older saved data (a 徒手 cell anywhere, no `content`) into that shape, and the scoring side still handles a 徒手 in any position. A-side deductions are computed as six checks (`aDeductions`: つなぎ技3人以上 / 宙返り連続2人以上 / 組運動 / 全員同時タンブリング / 複雑な同調性タンブリング — 同一スロットで2〜4人が同時に転回系 / 後半シリーズの難度), and E is manual per-series plus whole-routine. **The values themselves are still provisional** — see the `※今後対応` note in `TeamScorer`; §3.4.5.4's 欠点テーブル is not implemented on the team side.

### Conventions and gotchas

- **Nothing can be manipulated while the apparatus is in the air** (`handsEmptyFlags`): between a 投げ and its キャッチ the hands are empty — always for a single-apparatus event (stick, rope), and for clubs/ring during a 二つ投げ — so a `skill` there cannot carry `hasApparatus`. The skill that *performs* the throw (`isThrow`) still holds it at take-off, so it may. The same flags drive all three paths: `stripForApparatus` clears the flag for scoring, `SeriesCard` omits the 手具操作 checkbox for those blocks, and `autoTemplate` passes every generated tumbling series through the strip. That made §3.5.5.5(3) reachable only through its second branch, so `computeScore` implements the rule as written — an E-difficulty 転回系 held with the apparatus earns +0.1 with **either** a throw during a held skill **or** two operations (`heldThrow || ops >= 2`) — and since those are two branches of one bonus, they never stack: `apparatusOpBonus` is a single 0.1 for the whole routine (`some(b => b.appOp > 0)`), like `seriesBonus` and `jumpVarietyBonus`, the other 最大0.10点 bonuses. The throw during an E tumbling no longer adds a separate per-row bonus (the original prototype's `E_BONUS` did, which double-counted the same rule), so a 後方宙返り半ひねり(操作)→前宙(操作)→きりもみ(視野外投げ)→キャッチ series scores D 0.9: tumbling E 0.7 + 手具操作加点 0.1 + 視野外の技術加点 0.1.
- **Input the current apparatus cannot express is never scored** (`apparatusBlockers` / `stripForApparatus` in `analysis.ts`): the apparatus buttons, a 他の手具 series template, an imported JSON and a share URL all leave the series items untouched, so a `useapp` throw/catch tag, a `twothrow`/`lefthand` reqType, `catchTwo` or a `ropeJump` can survive into an apparatus whose editor offers no such input — invisible on screen yet still worth 技術加点 or difficulty (a real stick routine carried a hidden 手具を使ったキャッチ worth +0.1, and a leftover rope jump list is worth difficulty). `computeScore` strips those first (the same array comes back when there is nothing to strip, so the generator pays nothing), `IndividualScorer.changeApparatus` confirms and strips on an apparatus switch (naming what goes), and `loadSeriesTemplate`/`appendSeriesTemplate`/`loadRoutineTemplate`/`applyImportedData` strip silently. Add any new apparatus-specific input to both `apparatusBlockers` and `stripForApparatus` — and to `commonBlockers` (`templates.ts`), which is the same idea for 共通 templates.
- **Combinations that cannot be performed together are not offered in the editor** (a different axis from the per-apparatus gating above): the 2つ同時キャッチ checkbox appears only where both apparatus are in the air (`catchTwoFlags` — clubs/ring with nothing left in hand, i.e. during a 二つ投げ or two throws in a row; an already-set flag stays visible so it can be cleared), and 二つ投げ (`TWO_THROW_TAG`) and 手具を使った投げ (`USE_APPARATUS_TAG`) are mutually exclusive — throwing both leaves nothing to press with, so `SeriesCard` disables whichever is off while the other is on (`.is-disabled`), never the one that is on, so old data carrying both can still be fixed.
- **A 必須投げ tag can sit on a mid-skill throw too**: `SkillItem.reqTypes` mirrors the throw item's, and the editor offers 二つ投げ under この技の最中に投げ on clubs/ring (mutually exclusive with 手具を使った投げ, the same way as on a throw item). Everything that reads a throw item's `reqTypes` reads a throwing skill's as well — `thrownCount(item)` (2 apparatus leave the hand on a 二つ投げ, so `handsEmptyFlags`/`catchTwoFlags`/`checkApparatusFlow` all follow), `performedThrowTypes` (so the apparatus's 必須投げ is satisfied by a 二つ投げ mid-salto), the 二つ投げの徒手動作加点, `seriesSignature`, `apparatusBlockers`/`stripForApparatus` and `commonBlockers`. The generator still never builds one (`canTwoThrowTumbling` only allows the shapes that throw *before* the saltos) — the editor allows it, the auto candidates don't propose it.
- **`APPARATUS_REQUIRED_ELEMENTS` entries with an `auto` field are judged from the series input** (stick's 右投げ右受け, the 必須投げ of each apparatus, every apparatus's 転回系の投げ受け, and rope's four jump requirements — see `RequiredElementAuto`), not from the `apparatusElements` manual checkboxes — `computeScore` ignores the manual list for those, and `IndividualScorer` hides them from the checkbox card.
- **ダイビング (`DIVING_SKILL_ID`) is the one skill whose difficulty depends on where it sits**: 後方系, lands on the head, so nothing follows it (it is in `CHAIN_END_SKILLS`). On its own it is A, but **directly after a salto it is upgraded one step to B** (`DIVING_UPGRADED_DIFFICULTY`) — an A-difficulty skill in between (a ロンダート, a バク転) breaks the "連続" and leaves it at A. Because that depends on the position, it is resolved by `skillDifficultyAt(skillIds, i, junior, future)` rather than `skillDifficulty`, and both `calcTumblingDifficulty` (individual) and `calcChunkDifficulty` (team) map over positions instead of ids. It counts as a salto always (`isSalto: true`), so 宙返り→宙返り→ダイビング is a 三宙. The generator never builds one: `Skill.noAuto` keeps it out of `usableSkills`, so it exists for the editor only.
- **側転 is 徒手, not a 転回技** (`Skill.isHandElement`): it carries no `isConnectA`, so it never satisfies the つなぎ技 requirement, and `computeScore` skips it when collecting the 系統 for the 方向系 check — 側方系 is met by ロンダート or 側宙. It stays selectable as a 徒手動作 and still counts as one motion like the other A skills.
- **`connectNoApparatus` (つなぎ技のA難度に手具操作なし, −0.2) only looks at throw-free tumbling units** — a connect inside a 投げタン unit is not deducted.
- **単独で実施する徒手系要素（§7.3.1）**：`SOLO_HAND_ELEMENT_GROUPS` から選び `SaveData.handElements`（idの配列）に入る。群ごとの `scored` が扱いを決める — **跳躍**（§3.6.1 の表 12項目・難度は**個人列**）は徒手系難度の候補になり、投げ受けの徒手ユニットと**同じ上位3つの枠を争う**（同点はユニットが先）。同じ要素は何度実施しても1回だけ（§3.4.4、`duplicate`）。**柔軟**（前後開脚・左右開脚・ブリッジ、`SOLO_FLEX_ELEMENTS`）は**難度に数えず**、1つでも実施したかだけをA側で見る（`flexCheck` / `FLEX_ELEMENT_DEDUCTION` −0.1）。`computeScore` は `handElementRows`（`adopted`/`inTop` 付き）と `handElementScore` を返し、**Σ`seriesBreakdowns[i].handDiff` ＋ `handElementScore` ＝ `handScore`**（per-series だけでは合わなくなった点に注意）。入力は**徒手・構成タブ**の「徒手系要素（跳躍・柔軟）」カード（跳躍の難度だけは D に出る）。`FLEX_EQUIVALENT_JUMPS`（反り身の跳躍 j8/j9）は難度は跳躍のまま、柔軟性の実施としても数える（`countsAsFlex`）。団体の選択肢（`HAND_ELEMENTS`）とは別表なので団体側は変わらない。
- **A側の機械化（§7.4.1）**：`基本徒手` を並べると `BASIC_HAND_ELEMENTS[].parts` から **上半身／下半身の深い運動**の充足を判定し、不足1部位につき `DEEP_MOTION_DEDUCTION`（−0.1）。表の下3つ（その他上半身／下半身／全身の運動）は名前のある4つに当てはまらない動作の受け皿で、選んだ部位をそのまま満たす。手具操作は `HAND_OP_CHECKS`（2部位以上を通る操作・特性を生かした操作、未実施 −0.1 ずつ。**スティックだけ「左手の手具操作」が増える** — `HandOpCheck.only` で手具を絞り、画面も採点も `handOpChecksFor(apparatus)` を通す。§3.2 の**左投げ左受けとは別軸の評価**なので、必須要素が満たされていてもこのチェックは自動では立たない）と **身体を離れる手具操作**（回数入力。`OFF_BODY_REQUIRED_COUNT`=4 に不足1回につき −0.1）。この最後の項目が規則の「プロペラ回旋2回以上」を置き換えており、`APPARATUS_REQUIRED_ELEMENTS` からプロペラの行は外して**全手具**で判定する（`mens-rg-rules.md` §3.2 とは意図的に不一致）。入力は `SaveData.basicHands` / `handOps` / `offBodyCount` に乗り、ファイル・テキスト・共有URL・ドラフトを往復する。各項目は `tip`（`DEEP_MOTION_PARTS` / `HAND_OP_CHECKS` / `OFF_BODY_TIP`、手具の特性だけ `APPARATUS_CHARACTER_HINTS` の手具別の例が続く。「2部位以上」の部位は `BODY_PARTS` の6つ＝右腕・左腕・右足・左足・胴・首）を持ち、入力欄の注記・`title` ツールチップ・`ScoreSummary` のチェックリスト（`RequiredCheck.tip`）に同じ文が出る。
- **説明文は根拠のあるものだけ置く（§7.3.2）**：オーナー提示のもの（深い運動・手具の特性・身体の部位）と、**自動判定しているものをコードから要約したもの**（`RequiredCheck.tip` の必須要素チェック、`ArtDeductionItem.tip` の handVariety/tumVariety/appVariety/appInTumbling、`ScoreSummary` の投げ方・受け方／連続宙返りの行）だけ。§3.5.6.4 の主観評価だけの項目（リズム・空間・独創性・徒手の割合・運動量）と違反・欠如には**置かない** — 規則に定義が無く、こちらで基準を作らないため。
- **個人モードのUIは2つのタブ**（`IndividualScorer` の `tab` state。`"d"`＝**投げ・タンブリング**：適用規則・手具・シリーズ入力・実施減点、`"a"`＝**徒手・構成**：基本徒手・徒手系要素（跳躍・柔軟）・手具操作の多様性・手具別必須要素・欠点テーブル・違反）。state のキーは D/A のままだが、**タブ名は点数ではなく入力の中身**で分けている — 徒手系要素は跳躍の難度が D に出るし、投げ・タンブリング側にも実施減点（E）がある。ツールバーと `ScoreSummary`・`.action-bar` はタブの外で常に見える。
- **§3.5.6.4 の欠点テーブル（芸術と多様性の主観評価）は手入力**：`ART_DEDUCTION_ITEMS` が表と1対1で、`computeScore(…, {artDeductions})` が項目ごとに `clampArtDeduction` で 0〜`max` に丸めて `artDeduction`/`artRows` を返し、A減点に加算する。「投げ受けの操作」だけは自動判定（投げ方・受け方の種類不足）なので手入力の対象外。**「転回系の種類・組み合わせの多様性」（`tumVariety`）は裏で自動計算する**（`tumblingVariety` in `analysis.ts`）: an advanced routine meeting every requirement carries 9〜11 転回 including the A-difficulty ones, so 6〜8 saltos once those are removed — all different means no deduction, and every repeat (`repeats` = 実施数 − 種類数) costs `TUM_VARIETY_DEDUCTION_STEP` (0.1) up to the item's 0.50; A-difficulty 転回技 and 転回技 entered as 徒手動作 are not counted, and a different twist or posture is a different skill. The value comes back as `ScoreResult.tumVariety` but is **never applied to A on its own** — `IndividualScorer` puts an 自動計算 button next to that row which fills the manual field (the row's note shows the salto count and kind count). **ジュニアは「独創性の高い内容と表現」を既定で上限まで引く** (`JUNIOR_MAX_ART_ITEMS` / `withJuniorArtDefaults`, called from `IndividualScorer.toggleJunior`): junior level only sees it from a few top-class gymnasts, so flipping the toggle **on** writes the item's `max` into the manual field (and the row says so), and flipping it **off** clears only a value still sitting at `max` — a value the user lowered by hand stays. It is a UI default, not a rule: `computeScore` treats it as ordinary manual input. **「転回中の操作」(`appInTumbling`) has the same treatment** (`tumblingOperation` in `analysis.ts` → `ScoreResult.tumOperation`, its own 自動計算 button): it counts only the skills that *can* carry an operation — the ones whose checkbox the editor shows, so きりもみ系 and anything while the apparatus is in the air are out of the denominator — and maps the share that actually do onto `APP_IN_TUM_STEPS` (0.8↑ → 0, then 0.1/0.2/0.3, under 0.2 → 0.4). **Those thresholds are the app's judgement, not the rules'**, which is exactly why it fills a manual field instead of deducting on its own. The generator, on the other hand, carries the computed value as a real deduction in its evaluation, so **the more advanced the routine the smaller it gets** (measured on stick over 20 routines each: saltos/kinds 3.6/3.3 at a 1.5 cap up to 8.1/7.7 with no cap; average deduction 0.09/0.12/0.11/0.10/0.06 → 0.03/0.06/0.07/0.05/0.04 with the term, D unchanged).
- **`computeScore` returns everything the UI needs**, including `seriesBreakdowns` (per-series contribution rows) and `required`/`missing` (必須要素 checks). Add new derived values to `ScoreResult`, not as ad-hoc calculations in components.
- **`seriesBreakdowns[i].tumRows`/`handRows`** carry one row per unit with `adopted`/`inTop` flags so `SeriesCard` can strike out what doesn't count; `tumDiff`/`handDiff` sum only the top-3-adopted units, so Σ per-series = `tumblingScore`/`handScore`.
- **Single source of truth for sums:** `computeScore` computes `seriesBreakdowns` first, then the literal-sum globals (`techniqueBonus`, `apparatusOpBonus`, `twoThrowMotionBonus`, and the base of `noApparatusDeduction`) are derived by summing those breakdowns — so per-series rows and grand totals cannot drift apart. Every unit is a difficulty candidate — a second, third… throw in one series is never suppressed, it just tends to lose the top-3 cut. **Identical content counts once for difficulty across the whole routine** (§3.4.4): every unit carries a `signature` (tumbling/投げタン = the sequence of non-A skills, so 手具を持っての前宙 and 投げての前宙 collide per Q&A Q22; hand = the composition of motions between throw and catch (type → count, order-insensitive); rope = jump id; technique tags and the presence of a throw are excluded), and among units sharing a signature only the highest-scoring one is adopted (ties keep the earlier) — but only for difficulty. Bonuses, throw counts, tumbling counts and every A-side check still see it, and `ScoreResult.unitAdopted[i][j]` tells the UI which units were skipped. Units in a `notDuplicate` series get a series-scoped key so they never collide with another series. The genuinely-global values that can't be derived per-series (top-3 adopted `tumblingScore`/`handScore`, the single `seriesBonus`, direction/throwCount/saltoChain/variety deductions) are computed across all series. When adding a rule, decide which category it is.
- **Duplicate-series suppression:** `seriesSignature` detects identical series (`dupSignatureFlags`); `Series.notDuplicate` lets the user declare "same input, different routine" (differences the input can't express — arm use in シェネ, motion breakdown) and clears the flag, giving the effective `dupFlags`. A duplicate contributes **nothing to D** (difficulty, series/technique/apparatus/two-throw bonuses all zero, and its units are excluded from the top-3 adopted pools) and nothing to counts; A-side checks (direction, salto chain, connect, required elements) still see its units. Per-series logic guarded by `if (isDup)`/`if (dupFlags[i])` — preserve that guard when adding rules, and use `dupSignatureFlags` (not `dupFlags`) for anything that must stay visible after the override.
- **`other` (その他) throws/catches count every time**, even in duplicate series — note the `throwOtherCount`/`catchOtherCount` paths sit *before* the `if (isDup) return` guard in the variety counting.
- State edits use `structuredClone` for immutable updates. Import/export (individual only) round-trips `SaveData` (`{ version: 1, apparatus, junior, series, executionDeduction, apparatusElements, violations, artDeductions }`) via file download and a copy/paste JSON modal (`JsonModal`). **`src/scoring/share.ts`** packs the same shape into a share URL (`buildShareUrl` with lz-string into the hash, `consumeShareHash` on startup in `App.tsx`) — team mode shares its own `{ kind: "team", team }` shape. Anything added to the save format needs to survive both paths.
- **Templates** (`src/scoring/templates.ts` + `TemplateModal`, individual mode): named 構成 (`Series[]`) and シリーズ (`Series`) templates kept in `localStorage` under `mens-rg-scorer:templates:v1`. Saving strips `executionDeduction` and loading preserves the target series' own value — a template is construction only. Same name = overwrite (`upsert`); the per-series dropdown splits them into 共通/この手具/他の手具 (`splitByApparatus`), and saving defaults to 共通 whenever the content allows it (`defaultTemplateApparatus`); `normalizeTemplateStore` drops broken entries so a bad store never breaks startup. Saving the current routine as a template does not require opening the manager — it sits both in the top toolbar and in the sticky bottom `.action-bar` (total score + 構成を保存 + テンプレート), so a long routine never has to be scrolled back up. Each series carries auto-derived **tags** (`SERIES_TAGS`/`seriesTags` in `analysis.ts`: 投げ / 投げタン / 三宙 (`maxSaltoChain >= 3`) / つなぎ) shown in the series header and on template cards, and the manager filters templates by free text, those tags, and difficulty/D-score **ranges** (`templateMetrics`). The manager shows templates as cards (name, apparatus, series count, and a `describeSeries` summary like 投げ→前宙→キャッチ); picking one edits it with the very same `SeriesListEditor`/`SeriesCard` the scoring screen uses (`showExec={false}`), so there is one editing UI, not two. Layout switches on `useNarrow()` (`matchMedia("(max-width: 900px)")`): wide screens get cards left / editor right, narrow screens show only the cards and overlay the editor as a sheet with a 一覧 back button.
- **ランダム生成（`generate*.ts` / `autoThrows.ts` / `autoTumblings.ts` / `tumbling*.ts` / `unseenShapes.ts`）— 現行ルールの要約。重み・確率の実測値と経緯は [`docs/generator-notes.md`](docs/generator-notes.md)**（`generate.ts` の `generateRoutine`/`generateForApparatus`、`GenerateModal` が入口）。**採点側は生成の重みを一切読まない**。
  - **構造**：`generateOptions.ts`（入出力型）/ `generateWeights.ts`（調整値）/ `generateEvaluate.ts`（数える・`evaluate`）/ `generateSearch.ts`（`greedyAttempt` → `tuneAutoSeries` → `swapIn` → `upgradeTumblings` → `upgradeHandUnits` → `levelAdoptedDiffs` → `trimSpareOtherStyles` → `orderSeries`）。importer は `from "./generate"` のまま。投げは `autoThrows.ts`（`AUTO_THROW_PATTERNS` × 投げ方 × 受け方）、タンブリングは `autoTumblings.ts`（`tumblingTransitions.ts` が `tumblingPatterns`/`tumblingChain`/`tumblingWeights` から**導出**する遷移表を歩くだけ）。ユーザーのテンプレートを先に使い、足りない分を自動候補（`auto: true`）で埋める。`autoRatio` で自動シリーズの割合、`autoThrows`/`autoTumblings: false` で無効化。
  - **評価の1本の式**：`-(範囲外+上限超過)*100 - 必須要素の不足 + D + 難度プレミアム + A - 実世界の好み - タイブレーク`。探索は「この数字が上がったか」だけを見る。**重みは3段階**で、新しく足すときはどれかに揃える：①タイブレーク 0.005〜0.05（難度の刻み 0.1 未満。同点の中でだけ効く）②実世界の好み 0.1〜0.9（点数と引き換えになる）③必須要素・範囲（`REQUIRED_ELEMENT_WEIGHT` 10／不足1つ、範囲外 ×100）。
  - **頻度は2か所で決まる**：候補の引き（`pick.ts`、遷移表の weight）と評価の重み。技術加点が付く形は引きを下げても greedy が拾うので、**評価側で `earns` を打ち消して**頻度を引きに戻す。評価の重みを要求値に応じて下げる方式は崖になる（段階ではなくオン/オフ）ので避ける。
  - **要求値（`minScore`/`maxScore`）で形が変わる**：技の最大難度の梯子（`SKILL_MAX_DIFF_STEPS`、上限は含む側）、`basicLevel`（D 2.0 未満）、必須要素を必須にするか（`requiresAllElements`、3.0 以上）、投げ回数の最頻値（`preferredThrowCount`）、D 4.2 以上は全6ユニット E を先に（`aimsAllE`）、採用ユニットの難度差は1段以内（`unitDifficultyCeiling`）。
  - **「現実にあるが記録のない形」は `unseenShapes.ts` に1行足す**（`chance`/`earns`/`extra`/`count`）。需要が高いほど出やすく、低いほど出にくい。使うもの：左手の視野外投げ・背面キャッチ・投げタンの左手投げ。
  - **手具別の現実則**：クラブは二つ投げを手以外で受けない／横投げ以外を押さえつけで受けない、リングは手以外のキャッチ×横投げが多い、ロープは足で受けて終わる（`FINISH_CATCH_TAG`、クラブは押さえつけで終わる）、`splitCatch`（二つ投げ→キャッチ→押さえつけ）は二つ投げに押さえつけキャッチを付けない一般則の唯一の例外。**手以外／手具を使ったキャッチの後は投げない**（`NO_THROW_AFTER_CATCH_TAGS`）、視野外のキャッチの後は視野外の投げだけ不可（`NO_SAME_TAG_AFTER_CATCH_TAGS`）。**その他**は「規則上は同じだが実際は別の捉え方」を表す入力なので、不足の種類を埋めるときだけ使い、余りは `trimSpareOtherStyles` が落とす。横投げは種類数に数えるが技術加点は付けない。
  - **タンブリングの連鎖則**：次の技の系統は前の技の着地向き（`leadsBackward`/`endsFacingBackward`）で決まり、難度は基本的に下がる（`DIFFICULTY_RISE_AFTER` が例外）。`CHAIN_END_SKILLS`（きりもみ系・側宙・とび前転）の後には何も続かず、転宙の後は側宙だけ。後方宙返り半ひねりは延長、前半ひねりで終わらない、後方着地で終わらない（低得点のみ可）。投げの位置は切り返しでは投げない（きりもみの視野外投げは例外）。きりもみ系は手具操作なし。**どの技がなぜ出ないか**は遷移表（`__tests__/transitions.test.ts`）の1行を見る。
  - **タンブリングの最中に投げる／受ける形は上級者だけ**：どちらもD要求値 `THROW_IN_SKILL_MIN_SCORE`（4.0）未満では候補に入らず、入れるかは生成ごとに1回だけ引く（投げ `THROW_IN_SKILL_CHANCE` 0.4 ＞ 受け `CATCH_IN_SKILL_CHANCE` 0.2）。**受ける形は専用の形を持たず**、ふつうのタンブリングの候補のうち1本目の技がロンダート・前宙（`CATCH_IN_SKILL_SKILLS`）のものから派生させる — 投げを前に置き、その1本目で受け、**あとはそのタンブリングのまま続く**（手具が空中にあるのは1本目まで）。受け方は手具を使ったキャッチだけ（`CATCH_IN_SKILL_PRESS_CHANCE` 0.2、クラブ・リングのロンダート。視野外・手以外は付けない）。採点側も受けた直後に転回技が続けば1本の投げタンとして扱う（`catchSkillContinues`）。
  - **技の最中の投げに手具を使った投げを付けるのはクラブだけ・低確率**（`THROW_IN_SKILL_USE_APPARATUS_CHANCE` 0.1、`draws.useAppThrow`）。視野外の投げ（きりもみ）には付けない。手具を使った投げ＋横投げ（視野外でない）は手具を使ったキャッチ（押さえつけ）で受けてよい（受けは通常の `pressCatch` / `sideThrow` の抽選どおり）。
  - **ユーザーが触れるつまみ（生成のみに効く）**：`rarity`（0〜100、重みを1つの単調変換 `rarityExponent`/`rarityChance` に通す。その他は対象外）、`tumblingBalance`（0〜100、幅は小さい。構造的なので重みを上げて広げない）、`skillWeights`（技ごとの倍率。`SkillWeightModal`、`localStorage` の `mens-rg-scorer:skill-weights:v1` には1以外だけ保存、0は候補から除外、位置別の上書きの後にも掛ける）、大会レベル（`COMPETITION_LEVELS` で D 範囲を埋めるだけ）。
  - **「○○は出る？」は `npm run probe` で確かめる**（候補にあるか・生成に出るかを手具×上限×珍しさの表で）。
