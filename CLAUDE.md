# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Vite + React + TypeScript single-page app that calculates competition scores for Japanese **men's rhythmic gymnastics** (男子新体操) — 個人 (individual) and 団体 (team, 5-person) modes. The UI language is Japanese; domain terms below keep the Japanese names since they appear throughout the code.

Two rule documents live at the repo root — keep both and `src/scoring/constants.ts` in sync:
- **`mens-rg-rules.md`** — official scoring rules (2025 edition) translated from the PDF. Pure rules, no code references.
- **`app-scoring-spec.md`** — maps rules to app code: constant names, pipeline description, implementation status, TODOs.

## Commands

- `npm run dev` — Vite dev server (hot reload).
- `npm run build` — `tsc -b` typecheck (strict) then `vite build` to `dist/`.
- `npm run typecheck` — types only, no emit.
- `npm run preview` — serve the production build locally.
- `npm test` — vitest (single run); `npm run test:watch` to keep it running.

The scoring logic is covered by vitest suites in `src/scoring/__tests__/` (analysis / score / team / junior / templates / generate / tags / options / twist). **After changing scoring logic, add or update a test there and run `npm test` plus `npm run build`.** `test-reports/` holds the reports written by the `scoring-test` skill (`.claude/skills/scoring-test`), which walks one rule-compliance pass: compare `mens-rg-rules.md` against `src/scoring/`, add tests for an angle no past report covered, and file an issue for anything wrong.

## Architecture

The codebase splits cleanly into **pure scoring logic** (`src/scoring/`) and **UI** (`src/App.tsx` + `src/components/`). The UI holds state and renders; it contains no scoring math.

`App.tsx` is a thin shell holding a `mode` toggle and rendering either `IndividualScorer` (個人) or `TeamScorer` (団体, 5-person). Each scorer owns its own state. Styling is a **glassmorphism design system in `src/index.css`** (CSS custom properties + class names + hover/transition states) — components use `className`, not inline styles. Change visual tokens in the `:root` block. Every モーダル shares one `.modal-overlay` (`z-index: 1000`), so a modal opened **from inside another** needs `.modal-overlay.is-nested` (1100) or it renders behind and cannot be clicked — `SkillWeightModal`, opened from `GenerateModal`, is the one case (and it is rendered after the outer overlay so the DOM order matches too). Series input (`.skill-row`/`.skill-block`) is a horizontal flow on wide screens and **stacks vertically at ≤720px** (the `.arrow` connector rotates to point down), so phones never scroll sideways. Each item block ends with an `.item-actions` row — `.move-btn` arrows at both ends swap the item with its neighbour (`SeriesListEditor`'s `moveItem`, disabled at the ends; the arrows rotate to ↑↓ in the stacked layout) and the ✕ in the middle removes it.

The data model is a flat **list of `Series`**, each an ordered list of `items` (`src/scoring/types.ts`). Everything else is derived. Five item `kind`s (a discriminated union on `kind`):

- `throw` (投げ) / `catch` (キャッチ) — bracket an apparatus throw; `reqTypes` holds required throws (e.g. `twothrow`, `lefthand`), `throwTypes`/`catchTypes` hold optional technique tags.
- `skill` (タンブリング技) — a tumbling element referencing `SKILL_LIST` by `skillId`, with `hasApparatus` and `isThrow` (throw executed mid-skill) flags. Saltos can also be entered **parametrically** — base (後方宙返り/前宙) × ひねり回数 × 姿勢 (抱え込み/屈伸/伸身) — and the picker switches between the flat list and that builder (a 手動入力／一覧入力 button per block). `buildTwistSkillId` returns the existing `SKILL_LIST` id whenever the combination has one, so dedup signatures never split; only combinations missing from the list become a synthesized `tw:<base>:<twist>:<posture>` id, which `skillDef()` resolves into a full `Skill` via `twistName`/`twistDifficulty`. Difficulty follows §3.6.2: backward depends on twists alone, forward is one step higher for 伸身 (`twistDifficulty`). The list/builder choice is **per skill block** and defaults to the list (switching one leaves the other blocks alone, and nothing is remembered across blocks or reloads); only a synthesized `tw:` id opens in the builder, since the list can't edit it.
- `ropeJump` (ロープ跳び, rope only) — a jump from `ROPE_JUMPS` (`jumpId`) with an `isMoving6m` flag. The series' highest-difficulty jump becomes its own 徒手系 unit (`Unit.fromRopeJump`), and the jumps drive rope's four auto-judged §3.2 elements plus the 様々な跳び加点.
- `motion` (徒手動作) — empty-hand body motions referencing `MOTION_OPTIONS` (`HAND_MOTIONS` plus the 転回技 that can count as 徒手 — 側転/バク転/きりもみ etc.; `motionDef()` resolves either). Each carries a repeat `count` (blank in the UI = 0, and a 0-count motion is counted nowhere — see `motionTimes`) and, for シェネ, a `hands` flag plus a `handsType` (片手上げ/両手上げ/回旋/その他) — hands/no-hands and each hands type are different techniques (Q&A Q28), a unit mixing them gets one signature per variant so it collides with any of them (Q&A Q21), and その他 sets `Unit.neverDuplicate` so it never counts as a duplicate.

### The scoring pipeline (`src/scoring/`)

- **`constants.ts`** — all definition tables and tunable rule values (`SKILL_LIST`, `HAND_MOTIONS`, `DIFF_SCORE`, `*_BONUS`, `*_DEDUCTION`, `*_CAP`, `ADOPT_COUNT`, …). Change scoring values **here only**. Dropdown grouping lives here too: `skillOptionGroups(junior, flow)` splits tumbling skills into 前方系/側方系/後方系 (`SKILL_CATEGORY_ORDER`) and `motionOptionGroupsFor(prevMotionId)` splits 徒手動作 into 縦回転/横回転 (`MOTION_AXIS_GROUPS`; every 転回技 used as 徒手 is vertical) — both keep the existing within-group ordering, and the pickers render them as `optgroup`s.
- **Which 系統 can follow which (input aid, no score effect)** — `leadsBackward(prevSkillId)` (`constants.ts`) answers "does this skill finish facing backward": true for `BACKWARD_ENTRY_SKILLS` (ロンダート/バク転), for backward saltos with whole-number twists, and for **forward saltos with a half twist** (前宙半ひねり — you land facing back, so 後方系 can follow directly); false for backward half-twists (`twist % 1 !== 0`) and `FORWARD_LANDING_BACK_SALTOS` (ダイビング前宙). It only decides whether a ロンダート is needed, not what is offered: the **only** place the picker narrows is right after a ロンダート/バク転, where 後方系 is the sole group (`skillFlowAfter(prevSkillId)` returns the `SkillFlow` — `backward`/`forward`/`side` — that `skillOptions`/`skillOptionGroups` filter by, and a skill that's already selected stays in the dropdown as its own option). Everywhere else all three groups stay selectable — going back to 前方系 after a salto is impractical but possible — and when 後方系 is picked where `leadsBackward` is false the editor **inserts a ロンダート**: `needsRoundoffBefore(items, iIdx)` (`analysis.ts`) tells `SeriesListEditor.updateItem` to splice a `roundoffItem()` in front (a standing バク転 with nothing before it is left alone). Team mode reuses `skillFlowAfter` for the same filter but does not auto-insert (the lane is a fixed grid of slots).
- **`analysis.ts`** — per-series functions. `analyzeSeries(series)` is the heart: it walks `items` left-to-right and flushes a buffer into **units** whenever a `catch` is seen, and also at a 徒手 element that sits *between* tumbling skills (`unitSplitFlags`) — 前宙→前転→前宙 is three units (tumbling / hand / tumbling), each judged on its own, and the salto chain breaks there too. A 徒手 with no 転回技 on one side (the 前転 you land a 投げタン with) does not split, and **nothing splits while a throw is in the air**: between 投げ and キャッチ a mix of 徒手 and タンブリング keeps its existing judging as one chunk.
  - A run with **no throw** → a `tumbling` unit; `calcTumblingDifficulty` = first skill's value, +1 per additional non-A skill, +1 if any throw, capped at E.
  - A run **containing a throw** → a `throw` unit; difficulty is `max(handDiff, tumblingDiff)`. `calcHandDifficulty` derives hand difficulty from accumulated motion count (縦3動作 → forced E). A throw unit that also contains a skill is a **投げタン** (`isThrowTumbling`) and counts toward tumbling, not hand.
  - Also: `saltoFlags` (きりもみ/きりもみ転回 count as saltos only inside a salto chain — Q&A Q7 — and every salto test goes through it), `tumblingFlags`/`handMotionsOfSkill` (a skill that isn't 転回系 — an A skill outside a つなぎ, a standalone きりもみ — counts as 徒手 motions instead: A/きりもみ = 1, きりもみ転回 = 2, summed with the `motion` items; a unit with no 転回系 skill becomes a hand unit even without a throw), `maxSaltoChain`, `hasConnect`/`hasConnectWithoutApparatus` (つなぎ技 detection), `checkApparatusFlow` (in-hand/in-air validator, warnings only — no score effect), `seriesSignature` (dup detection).
- **十年後モード（F・G難度）** — a speculative mode the rules do not have: `FutureLevel` (`"F"` / `"G"` / `null`) raises the difficulty ceiling above E, with `DIFF_SCORE` F 0.9 / G 1.1. Only the **ceiling** changes — every place that used to stop at E goes through `maxDiff(future)` / `clampDifficulty(value, future)` (`twistDiffValue` extends the §3.6.2 step table to 4〜5 twists, `calcTumblingDifficulty`, `calcHandDifficulty`, team's `chainValue` / 5-person bump / crossing), while bonuses, deductions, required elements and dedup stay exactly as they are. `SKILL_LIST` entries flagged `future` are hidden unless the mode is on and their difficulty fits the chosen ceiling, and those flagged `teamOnly` (the mode's 2回宙返り系 — ルドルフハーフ / 後方伸身2回宙返り1回ひねり / リジョンソン, which individuals don't perform) only reach the team picker (`skillAllowed(id, junior, future, team)`; `skillBlockedReason` names why a skill is absent). Hand units reach F/G by a **weighted motion count** instead of a plain one (`HAND_MOTION_WEIGHT` / `futureHandValue`: 縦回転 — 前転・後転・徒手扱いの転回技 — costs 1.5 against 横回転's 1, because it eats more of the apparatus's air time; F from 5.0, G from 5.5), so シェネ×5 is F while シェネ×4→前転, 前転×4 and any 6 motions are G. That also made 縦3動作's E a **floor rather than an override** (`Math.max`), since the early `return "E"` had 縦3動作＋シェネ3回 scoring below a plain 6 motions once the ceiling rose. An existing skill can also be re-rated by the mode — `FUTURE_SKILL_DIFFICULTY` lifts ルドルフ from E to F, the same shape as `JUNIOR_SKILL_DIFFICULTY` — and `skillDifficulty(id, junior, future)` clamps to the ceiling so **turning the mode off never leaves an F skill scoring 0.9** (`skillDef` keeps the raw definition). The flag is threaded exactly like `junior` (`computeScore(…, {future})` → `analyzeSeries` → …, `TeamState.future`, `GenerateOptions.future`), and the generator treats the F/G skills as the one exception to "the vocabulary is the user's" (`usableSkills` in `tumblingTransitions.ts`) — nobody performs them yet, so they join the candidate pool even when no template shows them; with the mode off they are not in the transition table at all. The throw side gets its own future-only shapes (`AutoThrowPattern.future` / `throwPatternAllowed`: シェネ×5 for F, シェネ×6 / シェネ×4→前転 / 前転×4 for G), since the current shapes stop at 4 motions. The toggle plus its F/G dropdown is **hidden until the junior toggle is flipped `FUTURE_UNLOCK_TOGGLES` (10) times** (`useFutureUnlock`, remembered per device in `localStorage`, shared by both modes).
- **`score.ts`** — `computeScore(series, apparatus, opts): ScoreResult` is the single source of truth for the whole-routine **individual** score. `opts.junior` switches to the ジュニア適用規則 (§10 変更規則1): ダイビング前宙/後方宙返り半ひねり/後方伸身宙返り半ひねり are C instead of B (`JUNIOR_SKILL_DIFFICULTY`, read via `skillDifficulty(id, junior)`), the minimum throw count drops from 3 to 2 (`throwCountRequired(junior)`), 2回宙返り系 are hidden from the skill picker (`Skill.isDoubleSalto` / `skillOptions(junior)`), and throws are capped at 5 (`throwCountMax(junior)`) — the 6th onward count for nothing (difficulty, throw count, variety, required throws, technique bonus) and cost −0.3 each. The flag is threaded down to `analyzeSeries` / `calcTumblingDifficulty` and defaults to `false`. **Team mode has junior too**: the flag lives in `TeamState.junior` (round-trips through `normalizeTeamState`) and `computeTeamScore` passes it to `analyzeTeamSeries` / `calcChunkDifficulty` / the bonuses — same per-skill difficulties and double-salto ban, plus `JUNIOR_SKILL_COMBOS` (`juniorComboAt`), which judges バク転→後方伸身宙返り as a single C and takes the max against the plain chain and the 5-person bump. Junior also caps each series' execution deduction at 1.0 (`JUNIOR_SERIES_EXECUTION_MAX` via `clampSeriesExecution`) — **team only**; individual series and both modes' whole-routine deductions are uncapped. The UI calls it once (memoized) and renders the returned object. Final score = **D (難度, additive) + A (10 − deductions) + E (10 − manual execution deductions)**, both A and E floored at 0.
- **`team.ts`** — the 団体 (5-person) model and `computeTeamScore(team): TeamScoreResult`. Different data shape: a grid of `Series` × player `lanes` × `slots` of `Cell`s; horizontally-adjacent non-empty cells form a **chunk** whose difficulty reuses `SKILL_LIST`/`DIFF_*` (no throw +1, unlike individual). Team 徒手 is a different thing from individual 徒手: there is no apparatus, so the motion-count options are gone — a `motion` cell picks from the §3.6.1 table (`HAND_ELEMENTS`, 跳躍/バランス/倒立/柔軟) and scores its **団体 (5名実施)** value (`teamHandDifficulty`), never chains with neighbouring cells, and is not bumped by the 5-person rule. 徒手 also presumes all five members perform it, so it is a property of the series, not of a cell: `TeamSeries.content` is `"skill"` (転回 grid) or `"motion"`, toggled next to the 同時実施シリーズ button, and a 徒手 series is `mode: "allTogether"` with one lane, one slot and one element (`motionSeries()`) — no grid, no crossing or union groups. `normalizeTeamState` folds older saved data (a 徒手 cell anywhere, no `content`) into that shape, and the scoring side still handles a 徒手 in any position. A-side deductions are computed as six checks (`aDeductions`: つなぎ技3人以上 / 宙返り連続2人以上 / 組運動 / 全員同時タンブリング / 複雑な同調性タンブリング — 同一スロットで2〜4人が同時に転回系 / 後半シリーズの難度), and E is manual per-series plus whole-routine. **The values themselves are still provisional** — see the `※今後対応` note in `TeamScorer`; §3.4.5.4's 欠点テーブル is not implemented on the team side.

### Conventions and gotchas

- **Nothing can be manipulated while the apparatus is in the air** (`handsEmptyFlags`): between a 投げ and its キャッチ the hands are empty — always for a single-apparatus event (stick, rope), and for clubs/ring during a 二つ投げ — so a `skill` there cannot carry `hasApparatus`. The skill that *performs* the throw (`isThrow`) still holds it at take-off, so it may. The same flags drive all three paths: `stripForApparatus` clears the flag for scoring, `SeriesCard` omits the 手具操作 checkbox for those blocks, and `autoTemplate` passes every generated tumbling series through the strip. That made §3.5.5.5(3) reachable only through its second branch, so `computeScore` implements the rule as written — an E-difficulty 転回系 held with the apparatus earns +0.1 with **either** a throw during a held skill **or** two operations (`heldThrow || ops >= 2`) — and since those are two branches of one bonus, they never stack: `apparatusOpBonus` is a single 0.1 for the whole routine (`some(b => b.appOp > 0)`), like `seriesBonus` and `jumpVarietyBonus`, the other 最大0.10点 bonuses. The throw during an E tumbling no longer adds a separate per-row bonus (the original prototype's `E_BONUS` did, which double-counted the same rule), so a 後方宙返り半ひねり(操作)→前宙(操作)→きりもみ(視野外投げ)→キャッチ series scores D 0.9: tumbling E 0.7 + 手具操作加点 0.1 + 視野外の技術加点 0.1.
- **Input the current apparatus cannot express is never scored** (`apparatusBlockers` / `stripForApparatus` in `analysis.ts`): the apparatus buttons, a 他の手具 series template, an imported JSON and a share URL all leave the series items untouched, so a `useapp` throw/catch tag, a `twothrow`/`lefthand` reqType, `catchTwo` or a `ropeJump` can survive into an apparatus whose editor offers no such input — invisible on screen yet still worth 技術加点 or difficulty (a real stick routine carried a hidden 手具を使ったキャッチ worth +0.1, and a leftover rope jump is worth +0.3). `computeScore` strips those first (the same array comes back when there is nothing to strip, so the generator pays nothing), `IndividualScorer.changeApparatus` confirms and strips on an apparatus switch (naming what goes), and `loadSeriesTemplate`/`appendSeriesTemplate`/`loadRoutineTemplate`/`applyImportedData` strip silently. Add any new apparatus-specific input to both `apparatusBlockers` and `stripForApparatus` — and to `commonBlockers` (`templates.ts`), which is the same idea for 共通 templates.
- **Combinations that cannot be performed together are not offered in the editor** (a different axis from the per-apparatus gating above): the 2つ同時キャッチ checkbox appears only where both apparatus are in the air (`catchTwoFlags` — clubs/ring with nothing left in hand, i.e. during a 二つ投げ or two throws in a row; an already-set flag stays visible so it can be cleared), and 二つ投げ (`TWO_THROW_TAG`) and 手具を使った投げ (`USE_APPARATUS_TAG`) are mutually exclusive — throwing both leaves nothing to press with, so `SeriesCard` disables whichever is off while the other is on (`.is-disabled`), never the one that is on, so old data carrying both can still be fixed.
- **A 必須投げ tag can sit on a mid-skill throw too**: `SkillItem.reqTypes` mirrors the throw item's, and the editor offers 二つ投げ under この技の最中に投げ on clubs/ring (mutually exclusive with 手具を使った投げ, the same way as on a throw item). Everything that reads a throw item's `reqTypes` reads a throwing skill's as well — `thrownCount(item)` (2 apparatus leave the hand on a 二つ投げ, so `handsEmptyFlags`/`catchTwoFlags`/`checkApparatusFlow` all follow), `performedThrowTypes` (so the apparatus's 必須投げ is satisfied by a 二つ投げ mid-salto), the 二つ投げの徒手動作加点, `seriesSignature`, `apparatusBlockers`/`stripForApparatus` and `commonBlockers`. The generator still never builds one (`canTwoThrowTumbling` only allows the shapes that throw *before* the saltos) — the editor allows it, the auto candidates don't propose it.
- **`APPARATUS_REQUIRED_ELEMENTS` entries with an `auto` field are judged from the series input** (stick's 右投げ右受け, the 必須投げ of each apparatus, every apparatus's 転回系の投げ受け, and rope's four jump requirements — see `RequiredElementAuto`), not from the `apparatusElements` manual checkboxes — `computeScore` ignores the manual list for those, and `IndividualScorer` hides them from the checkbox card.
- **ダイビング (`DIVING_SKILL_ID`) is the one skill whose difficulty depends on where it sits**: 後方系, lands on the head, so nothing follows it (it is in `CHAIN_END_SKILLS`). On its own it is A, but **directly after a salto it is upgraded one step to B** (`DIVING_UPGRADED_DIFFICULTY`) — an A-difficulty skill in between (a ロンダート, a バク転) breaks the "連続" and leaves it at A. Because that depends on the position, it is resolved by `skillDifficultyAt(skillIds, i, junior, future)` rather than `skillDifficulty`, and both `calcTumblingDifficulty` (individual) and `calcChunkDifficulty` (team) map over positions instead of ids. It counts as a salto always (`isSalto: true`), so 宙返り→宙返り→ダイビング is a 三宙. The generator never builds one: `Skill.noAuto` keeps it out of `usableSkills`, so it exists for the editor only.
- **側転 is 徒手, not a 転回技** (`Skill.isHandElement`): it carries no `isConnectA`, so it never satisfies the つなぎ技 requirement, and `computeScore` skips it when collecting the 系統 for the 方向系 check — 側方系 is met by ロンダート or 側宙. It stays selectable as a 徒手動作 and still counts as one motion like the other A skills.
- **`connectNoApparatus` (つなぎ技のA難度に手具操作なし, −0.2) only looks at throw-free tumbling units** — a connect inside a 投げタン unit is not deducted.
- **§3.5.6.4 の欠点テーブル（芸術と多様性の主観評価）は手入力**：`ART_DEDUCTION_ITEMS` が表と1対1で、`computeScore(…, {artDeductions})` が項目ごとに `clampArtDeduction` で 0〜`max` に丸めて `artDeduction`/`artRows` を返し、A減点に加算する。「投げ受けの操作」だけは自動判定（投げ方・受け方の種類不足）なので手入力の対象外。**「転回系の種類・組み合わせの多様性」（`tumVariety`）は裏で自動計算する**（`tumblingVariety` in `analysis.ts`）: an advanced routine meeting every requirement carries 9〜11 転回 including the A-difficulty ones, so 6〜8 saltos once those are removed — all different means no deduction, and every repeat (`repeats` = 実施数 − 種類数) costs `TUM_VARIETY_DEDUCTION_STEP` (0.1) up to the item's 0.50; A-difficulty 転回技 and 転回技 entered as 徒手動作 are not counted, and a different twist or posture is a different skill. The value comes back as `ScoreResult.tumVariety` but is **never applied to A on its own** — `IndividualScorer` puts an 自動計算 button next to that row which fills the manual field (the row's note shows the salto count and kind count). The generator, on the other hand, carries the computed value as a real deduction in its evaluation, so **the more advanced the routine the smaller it gets** (measured on stick over 20 routines each: saltos/kinds 3.6/3.3 at a 1.5 cap up to 8.1/7.7 with no cap; average deduction 0.09/0.12/0.11/0.10/0.06 → 0.03/0.06/0.07/0.05/0.04 with the term, D unchanged).
- **`computeScore` returns everything the UI needs**, including `seriesBreakdowns` (per-series contribution rows) and `required`/`missing` (必須要素 checks). Add new derived values to `ScoreResult`, not as ad-hoc calculations in components.
- **`seriesBreakdowns[i].tumRows`/`handRows`** carry one row per unit with `adopted`/`inTop` flags so `SeriesCard` can strike out what doesn't count; `tumDiff`/`handDiff` sum only the top-3-adopted units, so Σ per-series = `tumblingScore`/`handScore`.
- **Single source of truth for sums:** `computeScore` computes `seriesBreakdowns` first, then the literal-sum globals (`techniqueBonus`, `apparatusOpBonus`, `twoThrowMotionBonus`, and the base of `noApparatusDeduction`) are derived by summing those breakdowns — so per-series rows and grand totals cannot drift apart. Every unit is a difficulty candidate — a second, third… throw in one series is never suppressed, it just tends to lose the top-3 cut. **Identical content counts once for difficulty across the whole routine** (§3.4.4): every unit carries a `signature` (tumbling/投げタン = the sequence of non-A skills, so 手具を持っての前宙 and 投げての前宙 collide per Q&A Q22; hand = the composition of motions between throw and catch (type → count, order-insensitive); rope = jump id; technique tags and the presence of a throw are excluded), and among units sharing a signature only the highest-scoring one is adopted (ties keep the earlier) — but only for difficulty. Bonuses, throw counts, tumbling counts and every A-side check still see it, and `ScoreResult.unitAdopted[i][j]` tells the UI which units were skipped. Units in a `notDuplicate` series get a series-scoped key so they never collide with another series. The genuinely-global values that can't be derived per-series (top-3 adopted `tumblingScore`/`handScore`, the single `seriesBonus`, direction/throwCount/saltoChain/variety deductions) are computed across all series. When adding a rule, decide which category it is.
- **Duplicate-series suppression:** `seriesSignature` detects identical series (`dupSignatureFlags`); `Series.notDuplicate` lets the user declare "same input, different routine" (differences the input can't express — arm use in シェネ, motion breakdown) and clears the flag, giving the effective `dupFlags`. A duplicate contributes **nothing to D** (difficulty, series/technique/apparatus/two-throw bonuses all zero, and its units are excluded from the top-3 adopted pools) and nothing to counts; A-side checks (direction, salto chain, connect, required elements) still see its units. Per-series logic guarded by `if (isDup)`/`if (dupFlags[i])` — preserve that guard when adding rules, and use `dupSignatureFlags` (not `dupFlags`) for anything that must stay visible after the override.
- **`other` (その他) throws/catches count every time**, even in duplicate series — note the `throwOtherCount`/`catchOtherCount` paths sit *before* the `if (isDup) return` guard in the variety counting.
- State edits use `structuredClone` for immutable updates. Import/export (individual only) round-trips `SaveData` (`{ version: 1, apparatus, junior, series, executionDeduction, apparatusElements, violations, artDeductions }`) via file download and a copy/paste JSON modal (`JsonModal`). **`src/scoring/share.ts`** packs the same shape into a share URL (`buildShareUrl` with lz-string into the hash, `consumeShareHash` on startup in `App.tsx`) — team mode shares its own `{ kind: "team", team }` shape. Anything added to the save format needs to survive both paths.
- **Templates** (`src/scoring/templates.ts` + `TemplateModal`, individual mode): named 構成 (`Series[]`) and シリーズ (`Series`) templates kept in `localStorage` under `mens-rg-scorer:templates:v1`. Saving strips `executionDeduction` and loading preserves the target series' own value — a template is construction only. Same name = overwrite (`upsert`); the per-series dropdown splits them into 共通/この手具/他の手具 (`splitByApparatus`), and saving defaults to 共通 whenever the content allows it (`defaultTemplateApparatus`); `normalizeTemplateStore` drops broken entries so a bad store never breaks startup. Saving the current routine as a template does not require opening the manager — it sits both in the top toolbar and in the sticky bottom `.action-bar` (total score + 構成を保存 + テンプレート), so a long routine never has to be scrolled back up. Each series carries auto-derived **tags** (`SERIES_TAGS`/`seriesTags` in `analysis.ts`: 投げ / 投げタン / 三宙 (`maxSaltoChain >= 3`) / つなぎ) shown in the series header and on template cards, and the manager filters templates by free text, those tags, and difficulty/D-score **ranges** (`templateMetrics`). The manager shows templates as cards (name, apparatus, series count, and a `describeSeries` summary like 投げ→前宙→キャッチ); picking one edits it with the very same `SeriesListEditor`/`SeriesCard` the scoring screen uses (`showExec={false}`), so there is one editing UI, not two. Layout switches on `useNarrow()` (`matchMedia("(max-width: 900px)")`): wide screens get cards left / editor right, narrow screens show only the cards and overlay the editor as a sheet with a 一覧 back button.
- **The generator's search side is split by role too** — `generateOptions.ts` (`GenerateOptions`/`GenerateResult`), `generateWeights.ts` (every tunable number: `A_PRIORITY`, the `*_WEIGHT`s, `DEFAULT_MAX_*`, `preferredThrowCount`, `requiresAllElements`, `suppressHardThrow`), `generateEvaluate.ts` (what gets counted — `hardThrowCount`/`otherStyleCount`/`saltoRepeatCount`/`shapeRankTotal`/… — plus `evaluate`/`shortfallPenalty` that add them up), and `generateSearch.ts` (`greedyAttempt`/`swapIn`/`tuneAutoSeries`/`orderSeries`/`upgradeTumblings`/`satisfying`). `generate.ts` keeps `generateRoutine`/`generateForApparatus` and re-exports all four, so importers still say `from "./generate"`. The evaluation reads `-(range + over-cap)*100 - shortfall + D + difficulty premium + A - real-world preferences - tie-breakers`, and its weights come in three scales: tie-breakers 0.005〜0.05 (under the 0.1 difficulty step, so they only decide between equal-scoring routines), real-world preferences 0.1〜0.9 (these do trade against points), and requirements/range (`REQUIRED_ELEMENT_WEIGHT` 10 per unmet element, ×100 out of range). Search only ever asks whether that one number went up.
- **`generate.ts`** builds a routine out of series templates: `generateRoutine(templates, {apparatus, junior, minScore, maxScore})` (and `generateForApparatus` when no apparatus is fixed) runs a randomized greedy over the usable templates (that apparatus + 共通), maximizing `-(out-of-range)*100 + dScore + aScore` — since missing required elements and junior over-throws land in the A deduction, that one number encodes "satisfy the requirements, push difficulty, stay in range" — then prunes any series whose removal doesn't lower the value, which is what keeps un-scored content (a 4th tumbling, a junior 6th throw, a duplicate series) out. 投げタン is capped at one per routine (`DEFAULT_MAX_THROW_TUMBLING`, overridable via `maxThrowTumbling`) — one satisfies the requirement, so extras carry the same penalty weight as falling outside the score range — Difficulty itself lowers a skill's pick weight (`SALTO_DIFFICULTY_WEIGHT`: D 0.6, E 0.3) because the harder a single skill is, the less often it appears; with that alone a max-D routine lands on 1〜2 D-or-above singles (the level a top Japanese routine actually carries), and `HIGH_DIFFICULTY_WEIGHT` (0.02) only breaks ties on top of it rather than capping anything. Ring is heavier and hard to twist while holding, so it gets fewer of those singles still: `APPARATUS_HIGH_DIFFICULTY_WEIGHT` (ring 0.4, via `apparatusHighDifficultyWeight`) multiplies the pick weight and divides the evaluation weight — measured, D-or-above singles average 1.24 (stick) / 0.96 (clubs) / 0.66 (ring) with the D score essentially unchanged. ハンドスプリング and 転宙 (`LIMITED_SKILLS`) are picked with a low weight and capped at `LIMITED_SKILL_MAX` (1) per routine, counting both skill and 徒手動作 entries (`limitedSkillCounts`), and タンブリング as a whole is capped at `DEFAULT_MAX_TUMBLINGS` (= `ADOPT_COUNT`, 3, counting the 投げタン, overridable via `maxTumblings`), since only the top three are ever scored. Packing 三宙 + つなぎ + 投げタン into three lines is tight for the greedy, so when the D target makes the 必須要素 mandatory and the best attempt still misses one, `swapIn` swaps single series against the remaining candidates (bounded rounds, only on the winning attempt, and it keeps the auto-series caps) before the result is returned; if a shortfall survives that, the generator rebuilds from a forced start — `satisfying` picks the candidates that cover the missing requirement and `greedyAttempt([t])` re-runs the greedy with that series pinned (up to `REBUILD_ATTEMPTS`, 5, per candidate, each followed by the same swap repair), which is what a routine sitting exactly at the D cap needs since covering the shortfall there means dropping a series, not adding one. D is raised through difficulty rather than bonuses: `DIFFICULTY_PREFERENCE_WEIGHT` (0.3 per point of `tumblingScore + handScore`) tops up the evaluation, so between two routines with the same D the one whose points come from difficulty wins, while the premium on 0.1 of difficulty (0.03) stays under the 0.1 D step so D is never traded away for it (measured over 40 routines: difficulty 3.90 → 3.93, bonuses 0.74 → 0.69, D unchanged). **An advanced routine's tumblings are almost all E**, so tumbling difficulty is preferred over hand difficulty on top of that (`TUMBLING_PREFERENCE_WEIGHT`, another 0.3 per point of `tumblingScore`), and since the greedy fills its `DEFAULT_MAX_TUMBLINGS` slots and never revisits them, `upgradeTumblings` runs one last `swapIn` restricted to tumbling candidates (`TUMBLING_UPGRADE_ROUNDS` 2) — that pass is what actually gets there: measured E share of tumbling units 67 % → 100 % with no D cap (tumbling difficulty 1.89 → 2.10, D 4.60 → 4.81, bonuses unchanged at 0.71) and 62 % → 87 % at a 4.5 cap, while a 2.5 cap stays at 20 % since a routine at that level genuinely does not perform E tumblings. How many throws a routine performs is shaped by the D target: `preferredThrowCount` is the mode (`THROW_COUNT_MODE_STEPS` — the rule minimum below D 2, 4 through the 2〜3 range, 5 from D 4, never below `throwCountRequired`), and `throwCountPenalty` pulls the count towards it — `THROW_COUNT_UNDER_WEIGHT` (0.1) per throw below it; above it the first extra throw costs `THROW_COUNT_OVER_WEIGHT` (0.2, or `THROW_COUNT_OVER_WEIGHT_HIGH` 0.15 from `THROW_COUNT_HIGH_SCORE` 5.0, where 6 throws get *more* common while the mode stays 5) and each further one `THROW_COUNT_FAR_OVER_WEIGHT` (0.3), because one throw over the mode is something a real routine does (a D 4-point routine may well perform 6) while two over is not (measured: D1.5 → 3 always, D2.5 → 4 at 80 %, D3.5 → 4 at 60 % with 5 at 40 %, D4.5 → 5 at 55 % with 6 at 40 %, no cap → 5 at 80 % with 6 at 20 %). These weights are above the 0.1 difficulty step on purpose: 技術加点 has no cap, so without them the greedy keeps adding throws past what a real routine performs. The rule minimum itself is never traded away — `shortfallPenalty` charges `REQUIRED_ELEMENT_WEIGHT` for an unmet throw count whatever the D target, and `Evaluation.throwCountUnmet` makes the swap/rebuild repair run for it too, so a low D cap lowers difficulty rather than dropping a throw. Difficulty is only ever chased with the first four throws (the 投げタン plus `ADOPT_COUNT` hand units); beyond that a throw exists for 技術加点 alone, which is allowed to add series rather than being capped away — `DEFAULT_MAX_AUTO_THROWS` (5) sits above the difficulty-adopted count so `throwCountPenalty`, not the pool cap, decides how many throws a routine performs (measured, 3 → 5: at a 4.5 target 6 throws go from 10 % to 40 %, D 4.08 → 4.18, 技術加点 0.59 → 0.71, generation time unchanged at ~0.37 s; a cap of 8 gives results identical to 5) — and `extraThrowOperation` × `EXTRA_THROW_OPERATION_WEIGHT` (0.01) keeps 徒手操作 out of the throws that difficulty never adopts. In a series with two 投げ受け the first is usually the harder one — which is mostly a matter of *which shapes exist*: `trailPair` puts the 徒手 on the first throw and a bare 投げ→キャッチ after it (mirroring `leadPair`), and that alone moved the split from 66 % / 34 % to 83 % / 17 % first-harder, where raising the weight below only reached 71 %. Its trailing throw comes from `trailThrowStyle` (never 手以外, the second throw of a pair) and its catch from `trailCatchStyle`, drawn as a 徒手なしの投げ受け (`MINIMAL_PATTERN`) so clubs' press catch and rope's foot catch appear there too — that catch is often what ends the routine. On top of that `reversedThrowOrderCount` × `THROW_ORDER_WEIGHT` (0.005) weakly disfavours the reverse — weakly, because real routines do it (the national rope routine opens 手以外の投げ→キャッチ→視野外の投げ→シェネ→キャッチ); 投げタン units are excluded since their difficulty comes from the tumbling. Repeating the same salto across the routine costs `SALTO_VARIETY_WEIGHT` (0.02) per extra occurrence (`saltoRepeatCount`; 前宙 is exempt via `REPEATABLE_SALTOS`) — below the 0.1 difficulty step, so variety only breaks ties and never trades away real points. Whether the 必須要素 are optional or mandatory depends on the D target: `requiresAllElements` is true when no upper bound is set or it is at least `REQUIRE_ALL_ELEMENTS_MIN_SCORE` (3.0), and `requireAllElements` overrides it either way, and each unmet requirement then costs `REQUIRED_ELEMENT_WEIGHT` (10) — enough to outrank any difficulty gain, but below the out-of-range penalty (×100) so the range still wins. `shortfallPenalty` is what counts them, and it also adds `A_PRIORITY` × `A_PRIORITY_WEIGHT` (0.01, below the 0.1 difficulty step) so that when they cannot all be met the ones that go are the ones a real routine gives up last: 投げの回数 = 各手具の必須投げ受け ＞ 投げタン ＞ D難度 (the `dScore` term itself) ＞ 多様な投げ受け ＞ つなぎ ＞ 三宙 ＞ つなぎの手具操作. Everything else in the evaluation is a straight D-vs-A comparison — `dScore + aScore`, same weight — so a series is taken only when the difficulty it adds beats the A deductions it brings (a 手具操作なし tumbling costs 0.2, a junior 6th throw 0.3, and so on); measured, the mandatory-elements rule costs about 0.07 of D+A on average, i.e. the comparison would usually pick the same routine anyway. Below that the shortfall is only the A deduction it already is, because a gymnast scoring 0〜1点台 genuinely does not meet them (the measured floor for a fully-compliant routine is about D 2.0). The greedy looks at the user's own templates first and fills what is missing from the auto candidates (`autoThrows.ts` / `autoTumblings.ts`), and `AUTO_SERIES_WEIGHT` (0.02, same idea as the variety weight) makes it prefer a template over an auto series on a tie. **How much of the routine may be auto-generated is the user's choice**: `autoRatio` (0〜1, a 0〜100 % slider in `GenerateModal`, default 1) is converted by `autoSeriesMax` into a count against `maxSeries` (`DEFAULT_MAX_SERIES`, 8) and enforced as a combined cap on auto series in both the greedy add (`greedyAttempt`) and the swap repair (`withinAutoLimits`); 0 builds no auto candidates at all, so the routine is assembled from the user's templates alone (measured with 3 templates: 0 % → 0 auto series and D 0.80, 25 % → 2 and D 2.51, 50 % → 4 and D 3.32, 75〜100 % → 5〜6 and D 4.04, where the per-kind caps bind first). Series order is not left to the greedy: `orderSeries` splits the chosen series into 転回系を含むもの (a tumbling unit or a 投げタン) and 投げ・徒手だけのもの and `interleave`s them so the routine alternates the way a real one does, keeping the greedy order only if the interleaved one scores worse (ordering is score-neutral except for junior's throw cap, which counts from the front). `GenerateModal` drives it.
- **Shapes that are physically possible but have no competition record** (a Japanese top-level gymnast might perform them) are declared in **one place**, `unseenShapes.ts` — adding one is a row in `UNSEEN_SHAPES`, carrying `chance` (a demand curve), `earns` (what the shape earns, which the evaluation cancels), `extra` (how much to dislike it on top) and `count(series)`. They are gated by demand rather than banned: `unseenChance(demand, curve)` with `UNSEEN_CHANCE_DEFAULT` is `base` (0.03) while the *demanded* D score is at or below `riseFrom` (4.5), then climbs `risePerPoint` (0.3) per point to `max` (0.4) — the mirror image of `HARD_THROW_FREE_SCORE`, which suppresses a shape *until* the demand is high. Three shapes use it: `leftHandNoViewThrow` (the **左手の視野外投げ**, an `AutoThrowStyle` flagged `rare`, stick only since 左手投げ is its 必須投げ; never dealt as a `leadPair`/`trailPair` throw), and the 通常の投げタン's `throwTumBackCatch` (**背面キャッチ**, `draws.backCatch` — dropped when a `secondThrow` follows, since 視野外で受けてそのまま投げる is impossible, and never combined with a 2つ同時キャッチ) and `throwTumLeftHandThrow` (**左手投げ**, `draws.leftHandThrow`). **Frequency is decided in two places, which is why the table exists**: the draw alone could not hold it down — each of these earns a 0.1 技術加点, so the greedy took a 3 % candidate share up to 55 % of routines — and making the evaluation weight *fall* with the demanded score produces a cliff, not a ramp (at 0.165 it is never taken, at 0.099 it always is — measured 1/20 then 13/20 across a 0.3-point change). So `generateEvaluate` charges `unseenPenalty` = Σ `count` × (`earns` + `extra`), which cancels exactly what the shape earns and hands frequency back to the draw. That cancellation is exact only where the gain is a 技術加点 tag (0.1 per tag, uncapped); where the gain is "satisfies a 必須要素" (投げタンの左手投げ) it cannot be cancelled — the requirement is worth `REQUIRED_ELEMENT_WEIGHT` (10) — so that shape declares `earns: 0` with `extra: 0.1` and is held down by the plain series that satisfies the same requirement being in the pool too (the requirement cancels out in the comparison). Measured per 20 stick routines: 左手の視野外投げ 0 with no demand, 2 at a 4.5 minimum, 4 at 5.0, 13 at 5.3; the 投げタン shapes stay at 0〜3 throughout.
- **`autoThrows.ts`** — the 投げ series the generator builds itself, so templates don't have to cover every 投げ方. `AUTO_THROW_PATTERNS` holds the shapes (投げ→1〜2回シェネ→前転→転がり→キャッチ / 投げ→1〜3回シェネ→前転→キャッチ / 投げ→3〜4回シェネ→キャッチ, the last two also with a 視野外投げ→視野外キャッチ pair appended, plus 投げ→前転3回→キャッチ — no シェネ, and 縦3動作 makes it E — plus the three minimal ones, 投げ→シェネ→キャッチ / 投げ→前転→キャッチ / 投げ→キャッチ (徒手0〜1動作), which are how an apparatus's 必須投げ (左手投げ / 二つ投げ) is most often satisfied with the least operation; being cheap they show up more as the D target drops, but they are not a low-level-only thing — and two `leadPair` shapes that put a 投げ→1シェネ→キャッチ *in front* of the main throw, which buys one more throw style with almost no extra operation (a consecutive pair's first throw is usually the harder one, so the cheap lead gets one シェネ — `LEAD_THROW_CHENE_COUNT`) the way the national rope routine opens 手以外の投げ→キャッチ→視野外の投げ→シェネ→キャッチ; the lead throw style is dealt as `leadThrowStyle` (its catch is a plain one, and 二つ投げ is never the lead since it needs a 2つ同時キャッチ)). `autoThrowSpecs(apparatus)` crosses every shape with every throw style the apparatus allows (`autoThrowStyles`: 通常 / 左手投げ or 二つ投げ / 視野外 / 手以外 / その他 / 手具を使った投げ) and deals out the catch style (`autoCatchStyles`: 通常 / 視野外 / 手以外 / その他 / 手具で押さえつけて — the last one clubs・ring only — plus two catches that satisfy **two** techniques at once, weighted down to `COMBINED_CATCH_WEIGHT` (0.1) since 技術加点 pays per tag: 視野外＋手以外 on every apparatus, governed by the same `NON_HAND_CATCH_RULE` so stick and clubs only perform it off a low-difficulty throw, and 視野外＋手具を使った on clubs・ring at any difficulty, with clubs lower still through `NO_VIEW_USE_APPARATUS_WEIGHT` (0.3) since it has no competition record; measured 1 % of catches on stick, 3〜5 % on clubs, 7〜16 % on ring), and the シェネの回数 round-robin (`cycler` reshuffles each lap), so candidates repeat as little as possible. The シェネの手 is drawn weighted instead (`handsWeight`/`HANDS_PICK_WEIGHT`): **手なし first** (1), then 片手上げ = 両手上げ (0.5), その他 (0.25), 回旋 (0.1) — and since 回旋 is mainly performed over at most two motions, `cheneCountWeight` lowers its weight on a shape with more (3 motions 0.3, 4 motions 0.1; the other hands don't change with the count), so a 3〜4回シェネ shape rarely draws it (measured on stick: 手なし 45 % / 両手 22 % / 片手 21 % / その他 10 % / 回旋 3 %, and 79 % of the 回旋 candidates sit at 1〜2 motions). `catchStylesForThrow` drops 手具で押さえつけてキャッチ from a 二つ投げ candidate — both apparatus are in the air, so there is none left in hand to press with — The 縦3動作 shape (投げ→前転3回→キャッチ, `verticalThree`) is normally received by pressing the other apparatus against it, so its catch style is drawn weighted (`VERTICAL_THREE_OTHER_CATCH_WEIGHT`, 0.2 for anything but 手具を使ったキャッチ) and `generate.ts` charges `VERTICAL_THREE_THROW_WEIGHT` (0.85 per series — more than the shape can add, so it only appears when the score genuinely needs it) for a 縦3動作 throw caught any other way (`verticalThreeThrowCount`) — so it only appears when the D range genuinely needs it (measured: 0〜1 per 20 routines with no range, but 9 of 10 once a 4.5 minimum makes it necessary). How readily a 手以外のキャッチ appears depends on the apparatus (`NON_HAND_CATCH_RULE`): stick performs it only off a low-difficulty throw (徒手 0〜1動作, `NON_HAND_CATCH_MAX_MOTIONS`), clubs only there and rarely (weight 0.2), ring and rope at the normal rate — A 手以外の投げ or 手具を使った投げ leaves no room for much afterwards — 徒手 0〜1動作 is what a gymnast realistically performs (`HARD_THROW_MAX_MOTIONS`), and a 転回系 in between essentially never happens — so `hardThrowCount` counts those throws followed by 2+ motions or any skill and `generate.ts` charges `HARD_THROW_WEIGHT` (0.9 per series, above the 0.7 an E hand unit can add) while the *demanded* D score stays at or below `HARD_THROW_FREE_SCORE` (5.0, via `suppressHardThrow` reading `minScore`), so the shape only appears when the range genuinely needs it (measured over 20 routines: with no demand ring 21 → 4 and rope 21 → 0 such throws, D 5.17 → 5.04 and 4.97 → 4.81; a 4.7 lower bound still produces 8 because the points are needed; above 5.0 the rule is off and it stays at 29). And since a rope routine very often finishes by catching the rope with the feet, that is one half of the **routine-ending catch** rule in `generate.ts` (`FINISH_CATCH_TAG`: clubs end by pressing the apparatus with the other one, rope by catching it with the feet; stick and ring have no fixed finish) — `finishCatchLast` moves the series ending on that catch to the end of the routine (score-neutral) and `FINISH_CATCH_WEIGHT` (0.05, under the 0.1 difficulty step so difficulty is never traded for it) makes the greedy pull such a series in when none of the chosen ones ends that way (measured over 20 routines each: reordering alone gets clubs 19/20 and rope 18/20, the weight takes them to 20/20 and 19/20 with the D average unchanged at 4.32/4.13). Measured over 25 routines each: 手以外 is 1 % of catches on stick, 1 % on clubs, 8 % on ring, 6 % on rope, and 7 of 25 rope routines end on one. Clubs and ring finish a roll — 転がり or 前転 — by pressing the apparatus with the other one, so `rollFinishShape` shapes weight every other catch down to `ROLL_FINISH_OTHER_CATCH_WEIGHT` (0.2) and a 投げタン rolling into its catch presses it with `ROLL_FINISH_PRESS_CATCH_CHANCE` (0.5, and `stripForApparatus` clears the tag on stick/rope where there is no second apparatus) — measured, 48 % of roll-finished catches on clubs and 53 % on ring are presses, the most common style on both. Continuing into a second throw out of a その他のキャッチ is unusual, so `OTHER_CATCH_BEFORE_THROW_WEIGHT` (0.2) down-weights it on the shapes that append one. **その他 is not a rare technique — it is the input that says "the rules call this the same catch, but in practice it is a different one", so it counts as another kind** toward 多様な投げ受け (`VARIETY_REQUIRED`, 3 kinds each way). The generator therefore uses it for exactly that and nothing else. `otherStyleUsage(series, r)` splits it three ways: the ones **filling a missing kind** are not disliked at all, the **spare** ones are charged `OTHER_STYLE_WEIGHT` (0.15, above the 0.1 技術加点 so decoration never pays for itself), and an その他 that is the routine's **first throw or first catch** is charged `OTHER_FIRST_WEIGHT` (1, above every real-world preference and below `REQUIRED_ELEMENT_WEIGHT`) — it declares "different from the ordinary one", so it cannot come before the ordinary one exists. On top of that, `trimSpareOtherStyles` **removes the tag outright** when it fills no kind (a meaningless declaration), looping `OTHER_TRIM_PASSES` (4) times because dropping one tag turns that throw into a 通常の投げ, which adds a kind and frees the next one; the trim is skipped if it would push the routine out of the requested D range. And because it is a bookkeeping device rather than a frequency, its draw weight (`OTHER_CATCH_WEIGHT` 0.1) is held **out of the rarity transform** — raising 珍しさ must not manufacture その他. Measured per routine at rarity 0/50/100: その他 tags 0.31/0.28/0.33, of which **spare 0 and leading 0 everywhere** (before: 0.86/0.64/2.06 with 20/13/5 spare), candidate share 9.3 %/2.4 %/0.7 %, D unchanged. The catch draw is therefore always weighted rather than round-robin. `catchStyleWeight` also makes a 視野外のキャッチ off a 左手投げ rare (`LEFT_HAND_NO_VIEW_CATCH_WEIGHT`, 0.1). Two throws inside one series constrain each other, and the rule has two halves. `NO_THROW_AFTER_CATCH_TAGS` is what **no** throw can follow (手以外 — a club caught with the feet is not thrown from there; 手具を使った — a pressed apparatus cannot be thrown), dropped by `catchStylesForPattern` from the shapes that append a second 投げ受け, tag-based so the combined catches are covered too; `autoTumblings` likewise drops the 投げタン's press catch when a `secondThrow` follows (measured: the press-catch-then-throw pattern occurred 147 times in clubs candidates and 13 times per 20 generated clubs routines, 145/17 on ring — now 0 everywhere). `NO_SAME_TAG_AFTER_CATCH_TAGS` is the narrower half: **視野外 blocks only a 視野外 throw** — catching out of sight and throwing out of sight cannot both be done, but catching out of sight and then throwing in plain sight is performed (視野外投げ→1シェネ→視野外キャッチ→二つ投げ→そのままキャッチ). So a 視野外 catch stays in the pool and the *throw* draw removes the collision instead (`trailThrowStylesAfter`, since a `trailPair`'s second throw is dealt after its catch; `noViewPair`, whose appended throw is always 視野外, still filters on the catch side) — measured 178/1128 catch→throw adjacencies on stick and 226/1280 on clubs are now 視野外 catches, 5〜6 per 20 routines. `throwStylesForPattern` drops from the `leadPair` shapes, whose main throw is the *second* one, both 手以外の投げ and **二つ投げ** — a second 二つ投げ carrying much 徒手 (i.e. at high difficulty) is not performed; the realistic shape catches it right away, which is what `trailPair` builds (measured: leadPair mains that were 二つ投げ 80/400 → 0, trailPair's second throw unchanged at 105/480). The lead throw itself may be 手以外, which is how the national rope routine opens. A `rare` style (`unseenShapes.ts`) is never dealt as a lead, trail or 投げタン second throw — those are round-robins, so it would appear at a fixed rate whatever the demand. `buildAutoThrowSeries` turns a spec into a `Series` — 二つ投げ is received with `catchTwo` so `checkApparatusFlow` stays clean — and `autoThrowTemplates` wraps them as `SeriesTemplate`s flagged `auto: true` (never saved to `localStorage`). Their names are just the kind (自動生成の投げ / 自動生成のタンブリング / 自動生成の投げタン) — the series content is shown next to the name, so the name carries no description. Each candidate keeps its `spec`, so `generateRoutine` can retune it: between the greedy add and the prune, `tuneAutoThrows` walks the chosen auto series and moves each one's シェネ回数 within its pattern's `cheneCountRange` while the evaluation improves — so a D-score cap is met by shortening a series rather than dropping it whole (and a lower bound by lengthening one). `generateRoutine` appends them to the pool but keeps at most `DEFAULT_MAX_AUTO_THROWS` (5) per routine — just enough that they never crowd out the templates, while the throw count itself is left to `throwCountPenalty` — and only where they raise the evaluation, so a routine need not contain any. `autoThrows: false` turns them off (the GenerateModal checkbox, and generator tests that want a fixed pool). A user template for the apparatus is still required: with none, `generateRoutine` returns null rather than building a routine of throws alone.
- **The per-skill pick weights are the user's to edit** (`skillWeights.ts` + `SkillWeightModal`, opened from `GenerateModal`). The measured tables (`SKILL_PICK_WEIGHT` and friends) are never rewritten — the store holds only a **multiplier per skill that differs from the default 1**, kept in `localStorage` under `mens-rg-scorer:skill-weights:v1`, so 全体リセット is "throw the store away" and 1技だけ戻す is "delete that key" (`resetSkillWeights`/`resetSkillWeight`, and `setSkillWeight` drops a key that is set back to 1). `normalizeSkillWeights` discards unknown ids, non-numbers and out-of-range values (clamped to `SKILL_WEIGHT_MIN` 0 〜 `SKILL_WEIGHT_MAX` 3, `SKILL_WEIGHT_STEP` 0.1) so a corrupt store never breaks startup. It rides through `GenerateOptions.skillWeights` → `autoTumblingSpecs` → `TransitionContext`, multiplying in `baseSkillWeights` **and again after the position-specific overrides** (`AFTER_BACK_LAYOUT_SALTOS`, `CONNECT_FINISH_RARE`, the テンポ row) so an edit is not silently erased where those tables replace the weight, plus the entry draw (`entryWeight`) — and a skill set to **0 is dropped from the candidate pool entirely** (`usableSkills`). It changes generation only: **scoring never reads it**.
- **How unusual the generated series are is the user's choice** (`GenerateOptions.rarity`, 0〜100, default `DEFAULT_RARITY` 50, a slider in `GenerateModal`). Every edge weight in the transition table already *is* "how often this is performed", so the knob is one monotone transform of those weights: `rarityExponent` maps 0 → `RARITY_COMMON_EXPONENT` (3, sharpening onto the most likely), 50 → 1 (exactly the measured frequencies) and 100 → `RARITY_RARE_EXPONENT` (−1, inverting them). `pickWeighted`/`pickDifferent` take that exponent (`rarityWeight`, and a weight of 0 stays unpickable even inverted), and the 0〜1 draws go through `rarityChance(p, rarity)` = `p^k / (p^k + (1-p)^k)`, which leaves 0.5, 0 and 1 alone and moves everything else the same direction — so a "rare series" means the rare *shapes* too (二つ投げ mid-tumbling, the きりもみ 視野外投げ, the つなぎ-after-second position, the unseen shapes), not just rare skills. `pick.ts` owns it since both `autoThrows.ts` and `autoTumblings.ts` draw through it; `cycler` round-robins are deliberately untouched (they exist to spread candidates evenly, not to model frequency). **The evaluation is not touched**, so a shape whose difficulty moves the score barely responds to the knob — what responds is everything score-neutral. Measured over 36 routines per setting, rarity 0/25/50/75/100: rare skills (ハンドスプリング・転宙・きりもみ系・テンポひねり) per routine 0.06 / 0.47 / 1.08 / 2.28 / 2.89, distinct skills used 17 / 22 / 24 / 25 / 24, D score 5.05 / 4.99 / 4.98 / 5.14 / 5.27. その他 is deliberately exempt (see below): it is a variety-bookkeeping input, not a frequency, so the knob neither manufactures nor suppresses it.
- **The generator's tumbling side is split by role** — `tumblingPatterns.ts` (the shapes: salto count, つなぎ, 投げ受け, `basicLevelPattern`), `tumblingChain.ts` (連鎖のルール — what may follow what and where a chain may end: `nextSaltoOptions`/`connectOptionsAfter`/`canEndChain`/`tumblingFlowErrors`), `tumblingWeights.ts` (how often it is actually performed: `SKILL_PICK_WEIGHT`/`saltoWeights`/`rollAfterChance`/`backwardEndChance` and every 0〜1 chance), `tumblingShape.ts` (`TUMBLING_SHAPE_ORDER` and the shape ranks), and `tumblingTransitions.ts`, which **derives** a transition table from the first two — `buildTransitions(ctx)` returns `first`/`next(prev)`/`connects(prev)`/`afterConnect(connect, before)`, each edge carrying `id`, `weight`, `endNever`/`endNeedsBackwardDraw`/`endNeedsRareDraw`, `rollChance` and `throwRule` (`ok`/`never`/`kirimomiDraw`). The table is never hand-written: the editor's constraints stay a question asked of `skillOptions`, so a picker change propagates. Candidate building (`autoTumblings.ts`) does nothing but walk that table, and "why is X never generated" is answered by pulling one row — not in the candidate list (a chain rule), small weight, can't end there, or can't throw there. `__tests__/transitions.test.ts` reads the table directly instead of reasoning from a seed. `autoTumblings.ts` re-exports all of them, so importers still say `from "./autoTumblings"`. The per-candidate draws live in one `AutoTumblingSpec.draws` (`TumblingDraws`: `backwardEnd`/`rareEnd`/`layoutAfterConnect`/`backToForwardThrow`/`roll`/`pressCatch`/`twoThrow`/`secondThrow`) so `withSaltoCount` reuses the same decisions, and the "may the chain end at n saltos" test is `chainEndsOk` alone. The draw helpers (`shuffled`/`cycler`/`pickWeighted`/`pickDifferent`) are shared from `pick.ts`.
- **`autoTumblings.ts`** — the タンブリング the generator builds itself, so templates don't have to enumerate every combination of the skills a gymnast can do. Two layers decide what is valid. **The editor's input constraints**: `needsRoundoffBefore` (a 後方系 needs a ロンダート in front unless the previous skill lands backward — the builder splices one in exactly like `SeriesListEditor` does) and the picker's own `skillOptions(junior, skillFlowAfter(prev))`, which `tumblingFlowErrors(series, junior)` re-checks each built series against (asking the picker rather than copying its logic, so it follows constraint changes). **And how routines are actually built**, which is what shapes a chain: `nextSaltoOptions(prev)` takes the 系統 from the previous skill's landing (`leadsBackward` → 後方系, otherwise 前方系/側方系) and caps difficulty at the previous skill's, since a chain steps *down* (後方1回半ひねり→前方1回ひねり→前宙); テンポ宙返り/テンポひねり (`TEMPO_SKILLS`) are the exception that may go up, and are the only 後方系 a chain continues past into another 後方系 — plain 後方系 chains are rare, so they stop; a **forward** salto that lands backward (前宙半ひねり) does continue into 後方系, which is how a real 三宙 like ロンダート→後方1回半ひねり→前宙半ひねり→ダイビング前宙 is built. The other exception is a 後方伸身宙返り (`isBackLayoutSalto`, twists included): it lands backward but is normally followed by 前宙・きりもみ・きりもみ転回 (`AFTER_BACK_LAYOUT_SALTOS`, 側宙 coming after that 前宙), so that list is returned — plus, at a low weight, the 抱え込み half-twists a minority of gymnasts do continue into (`AFTER_BACK_LAYOUT_BACKWARD_SALTOS`: 後方宙返り1回半ひねり / 後方宙返り半ひねり at 0.5 against 前宙's 5, only after a 後方伸身 that actually lands backward (a whole twist — off a half-twist one you would need a ロンダート, which is the つなぎ shape instead), and only where the difficulty does not rise, since a chain steps down — 後方伸身2回ひねり→抱え込み1回半ひねり is the shape; measured 13 of 366 continuations, 3.6 %). Those land forward, so the line can go on into a 前方系 and make a 三宙. 転宙 is the opposite case: **nothing follows it but a 側宙** (`ONLY_SIDE_SALTO_AFTER`) — no other salto, no つなぎ, and no 前転 either (it is in `NO_ROLL_AFTER_SKILLS`), so a 転宙 either ends the line or leads into a 側宙. The rest of the list is returned as-is — きりもみ系 only count as saltos inside a chain (Q&A Q7), which is exactly this position, so no difficulty ceiling applies — and it carries weights (`saltoWeights`) because the real split is 前宙 ＞ きりもみ ＞＞ きりもみ転回. きりもみ系 are not in `saltoList` at all (they only count as saltos inside a chain), so the one place they follow a **forward** salto is `AFTER_FORWARD_KIRIMOMI` (きりもみ転回 only — 前宙→きりもみ転回 is performed, e.g. 投げ→前宙→きりもみ転回→キャッチ; きりもみ is not, since landing on the neck and back cannot lead straight into a catch). The difficulty ceiling deliberately does **not** apply there — きりもみ転回's C is not "the chain stepped up" — and its `SKILL_PICK_WEIGHT` (0.3) puts it below 側宙 (1) and above 転宙 (0.2). Measured per 160 generated routines, chain-ending 側宙 98 / きりもみ転回 56 / 転宙 31; **the draw is a weak lever on that ratio** (halving きりもみ転回's weight to 0.15 only moves it 57 % → 49 % of 側宙's count, and 0.02 lands at 33), because the greedy takes a distinctive ending whenever one is in the pool — the same "frequency is decided in two places" shape as `unseenShapes.ts`, so pushing it lower means an evaluation weight, not a smaller weight here. `CHAIN_END_SKILLS` (とび前転・きりもみ — they land on the neck and back — plus きりもみ転回 and 側宙, which in practice only ever come last) end a chain: `nextSaltoOptions`/`connectOptionsAfter` return nothing after them and none of them is used as an entry or a つなぎ. 側転 is 徒手 now, so it is not a つなぎ either (it stays as the lead-in to a 側宙). `connectOptionsAfter(prev)` allows つなぎ技 only where they happen: ロンダート/側転/ハンドスプリング/とび前転 after a forward-landing salto, バク転 only after テンポ; `saltoOptionsAfterConnect` then picks from the 系統 that connect leads into, with `CONNECT_FINISH_RARE` (ただの後方宙返り) down-weighted rather than banned — advanced gymnasts finish a つなぎ with ダイビング前宙/後方伸身宙返り when they want a B, but a junior or a gymnast whose D sits in the 0〜1点台 does perform it. A 投げタン that throws first never starts with a ロンダート — apparatus air time only allows 前方系, finished with 前転 (`THROW_ROLL_MOTION`) or 側宙/転宙/きりもみ転回 (`THROW_FINISH_SALTOS` — measured 74 % / 10 % / 17 % of 800 candidates); throwing during the last salto instead (`throwInSkill`) has no such limit, since the air time only covers what follows the throw. A chain steps down in difficulty, with one named exception: `DIFFICULTY_RISE_AFTER` lets 後方宙返り半ひねり continue into the harder 前方宙返り1回ひねり (and on into a 前宙) because gymnasts do perform that, weighted down to `DIFFICULTY_RISE_WEIGHT` (0.3) since going up is otherwise rare. Under junior rules a low D target prefers the skills junior upgrades — `withJuniorBoost` multiplies ダイビング前宙 / 後方宙返り半ひねり / 後方伸身宙返り半ひねり (`JUNIOR_SKILL_DIFFICULTY`, all C for junior) by `JUNIOR_UPGRADE_BOOST` (2) while the target is under `JUNIOR_UPGRADE_BOOST_MAX_SCORE` (3.0). **How hard a single skill may be scales with the demanded D score** (`SKILL_MAX_DIFF_STEPS` / `maxSkillDiffValue`, read from `targetScore` = `maxScore`): C up to the 2点台, D through the 3点台, the full ceiling from 4.0, and no limit when no upper bound is given. Without it the generator met a low target by **adding elements rather than lowering difficulty** — measured, an E-difficulty single appeared even at a 2.0 cap, and the average skill difficulty was flat (2.27 at a 1.5 cap vs 2.66 at 5.0, on an A=1…E=5 scale) while the salto count tripled (3.0 → 7.8). With the ladder the hardest single is C/C/C/D/D/E/E across caps 1.5〜5.0, D-or-above singles per routine go 0 / 0 / 0 / 0.38 / 0.44 / 0.76 / 0.80, and the D score still lands on target (1.47 / 1.96 / 2.46 / 2.96 / 3.46 / 4.40 / 4.81). The per-skill *average* stays shallow by design (2.27 → 2.57): a chain steps **down** in difficulty, so most skills in any routine are B/C whatever the level — what the level shows in is the hardest single and how many chains there are. On top of that, **the top difficulty of the era is almost never performed as a single**: `TOP_SINGLE_WEIGHT` (0.05) replaces `SALTO_DIFFICULTY_WEIGHT`'s entry for whatever difficulty equals `maxDiff(future)` (`saltoDifficultyWeight`), since an E-difficulty *unit* is built as C→B→B rather than as one E skill — competition examples exist but are rare even at the national maximum of D 5.0〜5.1. Points-wise the greedy is indifferent (a single E and a C→B→B chain are both 0.7), so the draw governs: measured E singles per routine fell from 0.20/0.36/0.42/0.27 (caps 4.0/4.5/5.0/none) to 0.11/0.18/0.18/0.09 with the D score unchanged. Turning on 十年後モード moves that treatment up to F/G and returns E to an ordinary 0.3, which is what "the ceiling rose" means. **Three skills are harder than their rating says**, and their *frequency* is treated as one difficulty step higher (`HARDER_THAN_RATED`: 転宙, きりもみ, きりもみ転回 — the neck/back landings and the off-axis one). The difficulty **score** stays exactly as the rules have it; only two frequency reads change: `harderThanRatedWeight` multiplies the pick weight by `HARDER_THAN_RATED_WEIGHT` (0.6, the same C→D ratio `SALTO_DIFFICULTY_WEIGHT` uses), applied **after** the position-specific overrides so it also reaches `AFTER_BACK_LAYOUT_SALTOS`, which is where きりもみ actually appears; and `frequencyDiffValue` feeds the D-target ceiling, so きりもみ転回 (C, counted as D) drops out of a routine capped in the 2点台 entirely. A multiplier rather than a table re-lookup, because `SALTO_DIFFICULTY_WEIGHT` only distinguishes D and above — a B→C bump would be a no-op for 転宙/きりもみ. Measured per routine (caps 2.5 / 4.5 / none): 転宙 0.22/0.22/0.24 → 0.09/0.24/0.27, きりもみ 0.18/0.31/0.42 → 0.11/0.29/0.29, きりもみ転回 0.31/0.42/0.51 → **0.00**/0.27/0.27, with the D score unchanged. Skills of the same difficulty are not performed equally often, so `SKILL_PICK_WEIGHT` multiplies the pick weight: ロンダート (1) ＞ バク転 (0.5) ＞ ハンドスプリング (0.5, and `LIMITED_SKILLS`' `RARE_PICK_WEIGHT` 0.2 on top, so 0.1 in effect — entries and つなぎ; the entry draw deals entries round-robin so a rare entry mixed into that rotation would appear once per pass no matter its weight, hence `LIMITED_SKILLS` entries are marked used and drawn by weight alone: measured, handspring entries fall from 7 % of candidates to 1.0 %, つなぎ from 4 % to 2.9 %, and routines carrying one from 25〜45 % to 0〜15 %), 前方宙返り1回ひねり ＞ 伸身前宙 ＞ きりもみ転回, 側宙 ＞ 転宙, 抱え込み = 伸身 ＞ 屈伸, 前宙 ＞ 前宙半ひねり, and テンポひねり lowest of the backward C skills except the 屈伸 ones, which stay below it (ハンドスプリング and 転宙 are already at 0.2 through `LIMITED_SKILLS`), and `CONNECT_RISE_WEIGHT` (0.3) down-weights a つなぎ finish harder than the salto before it, since a chain steps down even across a connect (E is C→B→B, not B→C→B). After a テンポひねり the next skill is テンポ宙返り ＞ any other salto ＞ バク転: `AFTER_TEMPO_TWIST_WEIGHT` (3) boosts テンポ宙返り in `saltoWeights`, and `TEMPO_CONNECT_WEIGHT` (0.3) down-weights テンポ系 as the first salto of a つなぎ candidate, since a テンポ is the only place `connectOptionsAfter` offers バク転. A salto that lands facing backward — a backward salto with a whole-number twist, or a forward one with a half twist (`endsFacingBackward`) — is not where a line stops: `canEndChain` keeps it out of the last position. Ending on the **backward** one is something a low-scoring gymnast does, so it is drawn with `backwardEndChance` — halving per point of the D target and exactly 0 from `BACKWARD_END_ZERO_SCORE` (3.0, the level where a routine starts carrying chains in several series, same threshold as `REQUIRE_ALL_ELEMENTS_MIN_SCORE`) or with no cap at all (measured: 8 % of lines at a 1.5 target, 10 % at 2.0, 0 % from 2.5 up); the draw is stored on the spec (`allowBackwardEnd`) so `withSaltoCount` tunes within the same decision. 後方宙返り半ひねり lands forward, so nothing stops a chain from stopping there, but an advanced gymnast almost always continues into a 前宙 or 側宙 — `RARE_CHAIN_END_SKILLS` with `RARE_CHAIN_END_CHANCE` (0.1, and `basicLevel` always allowed) makes the builder extend the chain by one salto instead, dropping the candidate when it cannot continue (measured: 0 of 75 advanced lines end there, 側宙 24 and 前宙 18 lead instead). Ending on a **forward half twist** (前宙半ひねり, 前方1回半ひねり) never happens in competition, so it is excluded regardless of the draw, and a 2回宙返り is exempt from all of this since it neither continues nor connects. Since nothing may follow a backward-landing salto either, those skills simply drop out of advanced chains. Throwing during a 側宙 is rarer still — practice footage with clubs exists but no competition record — so `THROW_IN_SIDE_SALTO_WEIGHT` (0.1) down-weights 側宙 as the throwing salto of a `throwInSkill` chain. **That list has to hold every skill nobody throws during**, otherwise suppressing one promotes the next: `THROW_IN_SALTO_WEIGHT`/`throwInSaltoWeight` keys both 側宙 and きりもみ転回 at 0.1, because once きりもみ転回 became a forward-salto continuation it took 21 % of `chainThrowInSkill` endings against the deliberately-suppressed 側宙's 8 % (now it is out of that pattern's top six and 側宙 is back at 9 %). **Twisting a forward salto while throwing is quite hard** — the real example is a twist-free 前宙 (ロンダート→後方伸身2回半ひねり→前宙(投げ)→前転→キャッチ) — so `throwInSaltoWeight` also returns `THROW_IN_TWIST_SALTO_WEIGHT` (0.3, above the 0.1 of the two with no record at all) for **any** forward salto carrying a twist, decided by `Skill.twist` rather than a hand list precisely so that lowering 前方宙返り1回ひねり cannot promote 伸身前宙1回ひねり (measured: the throwing salto was 前方宙返り1回ひねり in 8 of 112 mid-skill throws, now 2 of 116, with 伸身前宙1回ひねり flat at 1〜2). Note the share is **redistributed, not removed** — 側宙 went 9 % → 16 % and 転宙 8 % → 10 % of mid-skill throws, because the throwing salto is the chain's last one and `pickDifferent` will not repeat the 前宙 the chain usually already carries; making the shape itself rarer would mean dropping the candidate rather than re-drawing its last salto. The つなぎ itself sits after the first salto by default (`DEFAULT_CONNECT_AT`) but also lands **after the second** on `CONNECT_AT_SECOND_CHANCE` (0.4) when the candidate can carry three saltos, since 前向きで終わる後方系→前宙→つなぎ→宙返り is a common series; a chain never ends on the connect (`endsOk` requires `n > connectAt`, and `withSaltoCount` keeps the post-connect salto) — measured 5 of 38 connect candidates and 2 per 20 generated routines, e.g. ロンダート→後方伸身宙返り半ひねり→前宙→ロンダート→後方宙返り1回半ひねり. Finishing a つなぎ with a **single 後方伸身 salto** (2回半ひねり→ロンダート→後方伸身1回半ひねり and stop) is not what advanced gymnasts do, so `layoutOnlyAfterConnect` rejects that chain length unless `LAYOUT_AFTER_CONNECT_CHANCE` (0.1, `basicLevel` always allowed) draws it, which makes the builder continue into a 前方系 instead (`AFTER_BACK_LAYOUT_SALTOS`) — measured 3 of 46 connect candidates → 0. And a chain that ends on a **forward** salto is normally followed by a 前転: `rollAfterChance(id, prevId)` appends one at `ROLL_AFTER_FORWARD_CHANCE` (0.9) for every forward salto but 前宙, which sits at `ROLL_AFTER_FRONT_CHANCE` (0.5) since both are performed, at `ROLL_AFTER_BACK_FORWARD_LANDING_CHANCE` (0.5) after a **forward-landing backward salto** (the half-twists and ダイビング前宙 — 前転, stopping there and continuing into a 前宙 are all normal, which is also the つなぎ-with-抱え込み case), at `ROLL_AFTER_SWITCH_CHANCE` (0.2) after a **切り返し** (a forward salto out of a backward-landing one, where a roll is usually not performed — the previous skill is read from the built items, so a つなぎ in between resets the orientation), and 0 after きりもみ/きりもみ転回/とび前転 (`CHAIN_END_SKILLS` — they land on the neck and back, nothing follows) or anything `noRollAfter` covers (measured over 15 candidate passes: 13 % of 切り返し endings roll, 48 % of forward-landing backward saltos, 50 % of 前宙, 73 % of other forward saltos, 0 % of 側宙/きりもみ); the roll is a 徒手動作 only, so **the score does not change** (a tumbling unit's difficulty comes from its 転回技 alone — measured D 0.80 either way). `NO_ROLL_AFTER_SKILLS` (側宙・転宙) plus `endsFacingBackward` **and `endsChain`** drop the closing 前転 of a `rollFinish` shape — nothing physically stops a roll out of a 側宙 but nobody does it, and a skill that lands on the neck, back or head cannot be rolled out of at all (that last part was the bug behind a generated …→きりもみ→前転→キャッチ: the in-chain roll `rollAfterChance` already returned 0 there, but the 投げタン's closing roll only consulted `NO_ROLL_AFTER_SKILLS` — measured 17〜20 per 447〜465 chain-ending skills, now 0). Because that shape can still arrive by hand, from an import or from old saved data, the rule is also a **warning**: `tumblingChainEndErrors(series)` names any 技/徒手動作 sitting after a `CHAIN_END_SKILLS` skill (a キャッチ is fine — 投げ→前宙→きりもみ転回→キャッチ is the point), `tumblingFlowErrors` includes it so the generator self-check covers it, and `SeriesCard` appends it to the `checkApparatusFlow` warnings (display only, no score effect). バク転 is never used as an **entry** (`TUMBLING_ENTRIES` backward is ロンダート alone) — adding one changes neither difficulty nor any requirement (only 宙返り−A−宙返り counts as a つなぎ), so it needs a reason to be there. Among shapes that reach the **same** difficulty there is still an order of how often they are actually performed — `TUMBLING_SHAPE_ORDER` plus `readTumblingShape`/`tumblingShapeRank`/`throwTumblingShapeRank` rank them (E: C→B→B ＞ D→B = C→C ＞ C→C→B ＞ B→B→B→B ＞ anything else ＞ a single E; D: C→B = B→B→B ＞ else ＞ a single D; 投げタン E: C＋側宙 = D＋前転 ＞ a つなぎ chain throwing on the last B ＞ a plain chain throwing on the last ＞ C plus a non-側宙 salto ＞ else ＞ a single E; 投げタン D: 前方C＋前転 = 前方B＋側宙/転宙 ＞ throwing inside a C series ＞ else), and `generate.ts` subtracts `shapeRankTotal` × `SHAPE_PRIORITY_WEIGHT` (0.005 per rank, so 3 tumblings at the worst rank stay under the 0.1 difficulty step — it only decides between equal-scoring routines). **きりもみ系 cannot carry 手具操作 at all** — きりもみ/きりもみ転回 land on the neck and back, so the apparatus cannot be manipulated during them (`Skill.noApparatusOp` / `canOperateApparatus`). All three paths honour it: the editor hides the 手具操作 checkbox, scoring ignores the flag even if saved data carries it (`analyzeSeries`'s unit flags, the 手具操作加点 op count, and the 手具操作なし deductions), and `applyApparatusOps` never picks one as the salto that carries the op (measured: 76 of 82 candidate きりもみ used to carry it, now 0 of 88, with the deductions still 0 and the bonus still 0.1 per routine). Throwing *during* one is still fine — that is releasing, not manipulating (`BACK_TO_FORWARD_THROW_CHANCE`'s きりもみ 視野外投げ). 手具操作 is applied only where it pays (`applyApparatusOps`): avoiding the A deductions needs just the last salto plus the つなぎ's A-difficulty skill, so that is all a non-bonus tumbling gets; an E-difficulty chain (the only difficulty that can earn §3.5.5.5(3)) gets a second salto for the two-operation branch, and a 投げタン gets none at all — the 手具操作なし deductions only look at throw-free series — except the `throwInSkill` skill itself when the unit reaches E, which earns the bonus through `heldThrow` (measured: 46 % of skills carry 手具操作 where it used to be 100 %, with the deductions still 0 and the bonus still 0.1 per routine). Opening with a ロンダート is preferred throughout: boosting a backward first salto is what pulls a ロンダート in as the entry, and a `throwInSkill` 投げタン gets `THROW_IN_SKILL_ROUNDOFF_WEIGHT` (3) whatever the D target (measured: 87 % of candidates and 71 % of generated 投げタン lines start with one). Normal tumbling is preferred the same way but **less and less as the D target rises** (`roundoffEntryWeight`: `ROUNDOFF_ENTRY_WEIGHT` 3 × `ROUNDOFF_ENTRY_DECAY` 0.7 per point, never below 1, and no preference at all with no cap — a routine chasing difficulty enters on whatever the difficulty needs), while a つなぎ shape under `ROUNDOFF_ENTRY_CONNECT_MAX_SCORE` (3.0) gets `ROUNDOFF_ENTRY_CONNECT_BOOST` (2) on top, since ロンダート→宙返り→つなぎ→宙返り is how a low-scoring routine satisfies the つなぎ requirement (measured share of candidates entering backward: 80 % at a 1.5〜2.0 target, 77 % at 2.5, 69〜70 % from 3.0 up, and 83 % vs 69 % for the つなぎ shapes). Nobody throws at the transition from a backward-landing salto into a forward one (`isBackToForwardThrow`), so those candidates are dropped — except きりもみ with a 視野外投げ, which is physically fine and looks good: `BACK_TO_FORWARD_THROW_CHANCE` (0.15) keeps it occasionally and `throwInSkillTypes` tags the throw 視野外. Half-twist backward saltos land forward, so 後方伸身宙返り1回半ひねり→前宙 with a throw is outside this rule and stays. A 投げタン's own throw can be a **二つ投げ** on clubs/ring (`twoThrow`, `TWO_THROW_IN_TUMBLING_CHANCE` 0.3, allowed by `canTwoThrowTumbling` only on the shapes that throw *before* the saltos — the editor does allow a 二つ投げ mid-salto, but the generator does not propose one): the series becomes 二つ投げ→タンブリング→2つ同時キャッチ, which satisfies the apparatus's 必須投げ and 転回系の投げ受け in one series; both apparatus are in the air, so the press catch is dropped and no skill in between carries 手具操作 (measured: 23 % of clubs and 19 % of ring 投げタン candidates, `checkApparatusFlow` clean, but only 0〜6 per 25 generated routines since a cheap 二つ投げ series satisfies the requirement just as well). A 投げタン can also be followed by a second 投げ受け inside the same series (`secondThrow`, dealt from `secondThrowStyles` — 手以外 is never the second throw, while stick's 左手投げ and clubs/ring's 二つ投げ are fine since the apparatus is back in hand); throwing before the salto makes that continuation more likely than throwing during it (`PAIR_AFTER_THROW_FIRST_CHANCE` 0.5 vs `PAIR_AFTER_THROW_IN_SKILL_CHANCE` 0.2, via `pairAfterChance`). `AUTO_TUMBLING_PATTERNS` holds the six shapes (連続1〜3本 / つなぎ技入り / 投げ受け＋前転 / 投げ受け＋側宙 / `connectThrowInSkill`: a つなぎ shape whose post-connect salto carries the throw (`connectAt` is `count - 1` for a `throwInSkill` pattern so the throw lands right after the connect, and the throwing salto is almost always ダイビング前宙 or 前宙 — `THROW_AFTER_CONNECT_SALTOS` × `THROW_AFTER_CONNECT_WEIGHT` (5) in `afterConnect`; measured 60 % ダイビング前宙 and 15 % 前宙 across 439 candidates, 1 of 20 stick and 7 of 20 clubs routines carry one). Because a connect resets which way the gymnast is facing, both the throw-position check and the 視野外 tagging read the **preceding item** rather than the previous salto (`chainEndsOk`'s `connectId` argument, `throwInSkillTypes(prevSkillId(items, …))`) — otherwise a ロンダート→…→ロンダート→前宙(投げ) would be rejected as a 切り返しの投げ / `throwInSkill`: a 2〜3-salto chain whose **last** salto carries the throw, finished 前転→キャッチ — the air time only constrains what comes after the throw, so the entry ロンダート and the chain in front are free, and one series then satisfies both 三宙 and 投げタン, which is how the national clubs routine does it: ロンダート→後方伸身2回半ひねり→前宙(投げ)→前転→キャッチ). **The vocabulary is the user's**: `generateRoutine` passes `usedSkillIds(own templates)` as `skillIds`, so the chains only combine skills the templates already show (a shape with no usable skill is skipped, not invented); with no templates at all the full skill list is used, which is what lets a routine be generated from nothing. Candidates carry their `spec` like the throws, so `tuneAutoSeries` can raise or lower a chain's 宙返りの本数 (`saltoCountRange` / `withSaltoCount`) to meet a D-score range, and at most `DEFAULT_MAX_AUTO_TUMBLINGS` (4 — three for the difficulty top-3 plus one that may carry a required element) go into a routine. A D target below `BASIC_LEVEL_MAX_SCORE` (2.0 — a gymnast scoring 0〜1点台) switches the candidates to `basicLevel`: what those routines actually look like is ロンダート→宙返り1本で終わり, no 三宙 (`BASIC_LEVEL_MAX_SALTOS` = 2), no つなぎ, and nothing above C (`BASIC_LEVEL_MAX_DIFF`), so the generator stops proposing a 2回半ひねり just because the total lands in range. `autoTumblings: false` turns them off.
- A template's apparatus can be **共通** (`COMMON_APPARATUS`): usable with every apparatus, allowed only when the series has no apparatus-specific input (`commonBlockers` — 二つ投げ/左手投げ/手具を使った投げ・キャッチ/2つ同時キャッチ/ロープ跳び); such templates are edited with those inputs hidden (`SeriesCard`'s `common` prop) and scored as stick (`scoringApparatus`).
- Team mode (団体モード) is fully wired for D/A/E, but the A-side deduction values are provisional (see `team.ts`) and §3.4.5.4 の欠点テーブル is individual-only so far; crossing-group detail and union-skill difficulty are still TODO.
