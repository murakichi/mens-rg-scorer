# resolve-issue — issue を1件片付ける（1イテレーション）

**1周で扱うのは1件だけ。** 複数を並行して抱えない（PR が混ざると人がレビューできない）。

## 使い方

```
/resolve-issue bug              # bug ラベルを古い順に1件
/resolve-issue bug,question     # どちらかのラベルが付いたものを古い順に1件
/resolve-issue #23              # 番号指定でその issue を扱う
/resolve-issue                  # ラベル指定なし（既定の優先順）
/loop /resolve-issue bug        # 延々と消化させる
```

引数の解釈：

| 引数 | 対象 | 並び |
|---|---|---|
| ラベル名（カンマ/スペース区切り、複数可） | **いずれか**のラベルが付いた open issue | 作成が古い順 |
| `#<番号>` / `<番号>` | その issue | — |
| なし | すべての open issue | 既定の優先順（下） |

**既定の優先順**（このリポジトリの運用。引数があれば引数が優先）：
`[blocked]`（作業が止まっている） > `bug`（採点が間違っている） > `[docs]` > `[idea]`。
接頭辞は `report-issue` スキルで起票されたときに付く目印。

## 1周の流れ

### 1. 候補を集める

```
gh issue list --state open --label bug --limit 30
```
`gh` が無い環境（Claude Code on the web など）では GitHub MCP の
`mcp__github__list_issues`（`state: "OPEN"`, `labels: [...]`, `orderBy: "CREATED_AT"`, `direction: "ASC"`）。

**除外するもの**：

- 既に PR が出ている issue（`gh pr list --state open` / `mcp__github__list_pull_requests` で
  本文に `Closes #N` があるものを確認）
- 直近に「判断待ち」コメントを書いて、オーナーの返信が無いもの（同じコメントを二度書かない）
- `wontfix` / `duplicate` ラベルが付いているもの

### 2. 1件選ぶ

引数でラベルが指定されていれば、その集合の **古い順に1件**。指定が無ければ既定の優先順 →
同順位なら古い順。番号指定ならそれ。選んだ理由は最後の報告に1行で書く。

### 3. 分類する

issue を読み、関連コード・ルールを確認したうえで、次のどれかに決める：

- **自力で片付く** → 手順4へ
- **オーナーの判断が要る**（仕様の選択、UI の方針、優先度）→ 手順6へ
- **もう有効でない**（実装済み・再現しない・重複）→ 根拠を1〜3行コメントして
  `gh issue close --reason "not planned"`（または completed）。手順7の作業ログを書いて1周を終える。

判断に迷ったら「オーナーの判断が要る」側に倒す。**採点ロジックの仕様は
`mens-rg-rules.md` を根拠に出せるときだけ自分で決める。**

### 4. 直す

- 変更は **その issue の範囲だけ**。ついで修正を混ぜない（気づいたら `report-issue` で別 issue）。
- 採点ロジック（`src/scoring/`）を触ったら **必ずテストを追加/更新** する
  （`src/scoring/__tests__/`、期待値はルールから手計算）。
- リファクタなら **挙動が変わらないこと** をテストで示す（既存テストが緑のまま）。

```
npm test
npm run build
```
両方緑になるまで直す。テストが落ちたまま次へ進まない。

### 5. コミットして PR

- ブランチ：`claude/issue-<番号>-<短いslug>`（環境から作業ブランチを指定されている場合はそれに従う）
- コミットメッセージは既存の履歴に合わせて日本語1行（例：`生成：手具ごとの重みを constants.ts に集約した (#63)`）
- `git push -u origin <branch>` → PR を作成し、本文に **`Closes #<番号>`** を入れる
  （`gh pr create` / `mcp__github__create_pull_request`）
- PR 本文には「何を変えたか」「ルール上の根拠」「テストで何を確かめたか」を各1〜3行。
- **手順7の作業ログを同じ PR に含める**（コード変更と同じコミットでよい）。

マージはオーナーが行う。**自分でマージしない。**

### 6. オーナーの判断が要るとき

issue に **選択肢と推奨** をコメントして、その周は終わる。

```markdown
## 調べたこと
<コード・ルールの該当箇所。file:line と §x.y>

## 選択肢
- A: <案> — 影響: <…>
- B: <案> — 影響: <…>

## 推奨
<A か B か。理由1〜2行>

決まれば実装します（どちらでも作業量は同程度 / A のほうが小さい など）。
```
ラベルが付けられるなら `question` を付ける。**コードは触らない。**
この場合も手順7の作業ログは残す（調べたことを次の周に渡すため。ログだけをコミットしてよい）。

### 7. 作業ログを書く（毎周必須）

`work-logs/YYYY-MM-DD-<slug>.md` を `work-logs/_TEMPLATE.md` から1本作る。日付は環境の今日の日付。
必ず埋めるのは **対象issueと選んだ理由 / 調べたこと（ルール§・`file:line`）/ やったこと /
`npm test`・`npm run build` の結果 / 結果（PR・issueの扱い）/ 申し送り**。
同じ日に2本目なら `-2` を付ける。コードを触らなかった周（判断待ち・クローズ）でも書く —
**調べて分かったことが次の周の入力になる。**

### 8. 報告（1行〜数行）

- 扱った issue 番号とタイトル（どの対象集合から選んだかも）
- 結果：PR 作成 / コメントして判断待ち / クローズ
- 残っている対象 issue の件数
- 書いた作業ログのパス

**候補が1件も無ければ**「対象 issue なし」とだけ報告して終わる（作業ログも不要）。
`/loop` を止めるかはオーナーが決める。

## やらないこと

- 1周で2件以上の issue を触る
- ルールの根拠なしに採点値・採点仕様を変える
- 大きなリファクタを一息でやる（分割して、残りは `report-issue` で起票）
- テストを skip / 削除して緑にする
- 自分で PR をマージする、issue を根拠なくクローズする
- 作業ログを後からまとめて書く（1周ごとに1本、その周のうちに）
