# report-issue — 気づきを issue にする（1件）

作業中に「これは今のタスクの範囲外だが放置したくない」と思ったものを **issue 1件** にして、
すぐ元の作業へ戻るためのスキル。**起票がゴールで、その場で直すのはゴールではない。**

## 起票するもの

| 種別 | タイトル接頭辞 | ラベル | 例 |
|---|---|---|---|
| 詰まり（判断・情報がないと進めない） | `[blocked]` | `question` | ルールが規定していない境界条件、どちらの仕様が正か決められない、ローカルで再現できない |
| 改善・リファクタ・欲しいツール | `[idea]` | `enhancement` | 同じロジックが3箇所にある、テストヘルパーが欲しい、生成器の重みを調整したい |
| ドキュメント | `[docs]` | `documentation` | CLAUDE.md が肥大化して読み切れない、spec と実装がずれている |
| 採点バグ（ルールとの食い違い） | なし（従来どおり） | `bug` | `scoring-test` スキルの手順6に従う |

接頭辞は `resolve-issue` が拾うための目印なので **必ず付ける**（ラベルは付かなくても可）。

## 起票しないもの

- 今のタスクの範囲内で、その場で直せること → **直す**（issue にして先送りしない）
- 「あとで見る」程度の感想、再現手順も影響も書けないもの
- 既に同じ issue があるもの → 重複を作らず、必要なら既存 issue にコメントする

## 手順

1. **重複確認**（必須）
   - `gh issue list --state open --search "<キーワード>"`
   - `gh` が無い環境（Claude Code on the web など）では GitHub MCP の
     `mcp__github__list_issues` / `mcp__github__search_issues` を使う。
2. **種別とタイトルを決める** — 接頭辞 + 40字以内の要約。何が問題かがタイトルだけで分かること。
3. **本文を書く**（下のテンプレ）。`file:line` を添える。推測は推測と書く。
4. **起票する**
   ```
   gh issue create --title "[idea] 生成器の重み定数が constants.ts と generate.ts に分散している" \
     --label enhancement --body "$(cat <<'EOF'
   ...
   EOF
   )"
   ```
   MCP なら `mcp__github__issue_write`（`method: "create"`）。
   ラベルが存在しないと作成に失敗するので、失敗したらラベルを外して再実行する。
5. **元の作業に戻る。** 起票した番号は、そのタスクの報告（レポート / PR / 返信）に1行で残す。

## 本文テンプレ

```markdown
## 何に気づいたか
<1〜3行。どこで作業していて何が気になったか>

## 根拠
<mens-rg-rules.md §x.y の引用 / src/scoring/xxx.ts:123 / 実行したコマンドと出力>

## 今どうしたか
<回避した / 保留した / 何もしていない。判断を保留したなら何を仮定したか>

## 提案（あれば）
<こうすると良いのでは、という案。複数あるなら選択肢と推奨を書く>

## 判断が必要なこと（[blocked] のみ）
<オーナーに決めてほしいことを疑問文で。決まれば作業が進む形にする>
```

## 注意

- **採点ロジック（`src/scoring/`）の仕様変更は勝手に入れない。** ルール（`mens-rg-rules.md`）を
  根拠に出せないものは issue にして判断を仰ぐ。
- 1件1issue。まとめて書かない（`resolve-issue` が1件ずつ潰せる粒度にする）。
- 巨大なリファクタ案は「最初の1歩」で切って起票する。
